# Decisions

Durable design decisions and the reasoning behind them.

This file answers **"why is it like this?"**. `CLAUDE.md` answers **"how do I
work here?"** — commands, conventions, checklists. When a rule in CLAUDE.md
needs a paragraph of justification, the justification belongs here and the
rule stays there.

Entries are append-only in spirit: when a decision is reversed, mark it
superseded and say what changed rather than deleting it. A decision that
turned out wrong is more useful than no record — see D-010, which exists
precisely because a feature was marked done without evidence.

**Format**: context (what forced a choice) → decision → consequences
(including what it costs), and a date on the heading. No template ceremony
beyond that. The date is not decoration: entries written against open work
say "pending at the time of writing", and once that work lands the clause is
only readable if the file says when it was written.

## D-001 — Evergreen soft-typing: preserve unknown data, never reject it (2026-08-16)

**Context.** The Gemini API adds enum variants, content types, and fields
without warning. A client that rejects what it doesn't recognize breaks on
someone else's release schedule.

**Decision.** Follow the [Evergreen spec](https://github.com/google-deepmind/evergreen-spec):
unrecognized values deserialize into `Unknown` variants that preserve the
original JSON, enums are `#[non_exhaustive]`, unknown data round-trips intact,
and polling continues on unrecognized status (bounded by timeouts).

**Consequences.** Callers must handle wildcard match arms. Every new enum
costs three helper methods (`is_unknown`, `unknown_<context>_type`,
`unknown_data`) and a round-trip test. In exchange, an API addition is a
`warn!` rather than an outage.

Unknown *fields* on a known variant were dropped until #491 (2026-11-04):
the hand-written `Step`, `StepDelta`, `Content` and `Annotation`
deserializers read only what they modeled. Each known variant now keeps the
rest in an `extra` map, so "round-trips intact" covers fields as well as
types.

Strict mode inverts this for tests that want to *find* unknowns: an
unrecognized value in `Content`, `Step`, or any string enum (every one is
generated by the crate-private `wire_enum!`, so they share one deserializer)
becomes a deserialization error. It is the `--cfg genai_strict_unknown` flag;
until D-030 (2026-11-06) it was the `strict-unknown` Cargo feature. The
other tagged unions (`Tool`, `StreamChunk`, …) ignore the flag. `StepDelta`
keeps a delta of an unknown `type` as `Unknown` either way, but under the
flag a known delta holding a value strict mode rejects (an unknown
`arguments.language`, an unknown content type in a `thought_summary`) fails
and names the field, as the matching `Step` does.

*Stated as a rule in CLAUDE.md ("Rules" → "Evergreen soft-typing").*

## D-002 — Response structs are `#[non_exhaustive]`; no struct literals (2026-08-16, revised 2026-09-24)

**Context.** Response types grow fields as the API does. If users can build
them with struct literals, every added field is a breaking change.

**Decision.** Response structs carry `#[non_exhaustive]`. Outside the crate
that bars struct literals, including `..Default::default()` functional-update
syntax. It does not bar construction: a type that derives `Default` can still
be built with `T::default()` followed by public-field assignment, which is
the supported route for test fixtures (`InteractionResponse` is one).

Request-side types are exempt: callers build those, and closing them would
cost struct-literal construction while buying the crate nothing.

**Consequences.** Fields can be added without a breaking change, and users
cannot hand-build a response to test against — which is the point: response
types represent API responses, and mocking them gives false confidence.
Test against the real API, or mock at the HTTP layer
(`ClientBuilder::with_base_url` points a client at a local server).

`tests/non_exhaustive_responses.rs` enforces the attribute on every
deserializable public struct in `src/` outside an explicit request-side
allowlist. Borrowed view types (`FunctionCallInfo`, `ToolCallInfo`, …) are
not deserializable, so the scan does not see them; those with public fields
carry the attribute by hand. Enums are not scanned.

*Also stated as a rule in `docs/ENUM_WIRE_FORMATS.md` ("Structs and `#[non_exhaustive]`").*

## D-003 — Antigravity alias enums deliberately break round-trip fidelity (2026-08-16)

**Context.** The Antigravity harness renames enum values between revisions.
`STATE_IDLE` became `STATE_FULLY_IDLE` in 0.1.5 → 0.1.10, and treating the old
spelling as `Unknown` is exactly what caused that breakage — every turn hung
to timeout.

**Decision.** These enums accept alias wire values and re-emit the *canonical*
current-harness spelling. `STATE_IDLE` in, `STATE_FULLY_IDLE` out.

**Consequences.** A deliberate departure from D-001's round-trip principle,
and worth naming as such. It is safe here because these are inbound-only
enums — the client never sends a `TrajectoryState` — so the asymmetry cannot
reach the wire. What it bought was one build driving either harness revision.

*Update 2026-09-24:* 0.1.18 changed an **outbound** shape (the user message
became a multi-part `UserInput`; the old plain string is rejected harness-side,
visible only on its stderr). Outbound shapes cannot be aliased, so aliases now
only let a build *read* older revisions; each build *drives* exactly
`SUPPORTED_HARNESS_VERSION`. The 0.1.5 aliases are kept but unreachable.

*Also stated as a rule in `docs/ENUM_WIRE_FORMATS.md` (Antigravity enums section).*

## D-004 — Verify API surface from generated bindings first, prose docs last (2026-08-16)

**Context.** Three sources describe the API and they disagree, consistently
in one direction. Video `processing` is a ~127x token-cost lever: 455 input
tokens for a clipped static window against 57,775 for agentic (#419, modeled
in #434). It appeared in the `google-genai` 2.18.1 bindings and on *neither*
`ai.google.dev` page. It is absent from 2.17.0, the version the gap tracker
had last been swept against when this was written, so the sweep that
concluded "fully covered" could not have seen it. The widened
`speech_config` union was the same shape, found one sweep earlier.

Conversely, the bindings describe a Retrieval tool and an
`enable_bigquery_tool` flag that the endpoint rejects as Vertex-only. The
live-verification notes in `docs/ENUM_WIRE_FORMATS.md` (its
"Tool::Retrieval" and "Deep Research agent_config" sections) record the
rejections. They are
cited by section rather than line: that file is edited on every sweep (see
D-011), and this entry's argument is that prose should not be taken at its
word, including this paragraph.

**Decision.** Rank sources: (1) generated bindings from `google-genai`, which
ship ahead of prose; (2) live probes, which are ground truth and often
narrower than the spec; (3) prose docs, including this repo's own, which lag
both. New surface found at rank 1 must be live-probed before being modeled as
usable.

**Consequences.** "Absent from the docs" is not evidence of absence, and
"present in the bindings" is not evidence of support. `docs/INTERACTIONS_API_GAP.md`
is a point-in-time snapshot, not a completeness guarantee. Since #438 its
header states the SDK version and date it was last swept against (the
baseline also lives in `.github/last-swept-sdk-version`), and the
`api-surface-sweep` workflow opens an issue when a newer SDK ships.

Getting this ordering backwards is what let video `processing` sit unmodeled
behind a "surface fully covered" conclusion that was false (#421) — the
sweep was real, and a version behind.

## D-005 — Spec-present but API-rejected: remove, or keep for parity? (2026-08-16)

**Context.** Several fields exist in the generated bindings but are rejected by
the Gemini endpoint. They fall into two groups, and the API's own error text
distinguishes them.

**Decision.**

| Error shape | Meaning | Action |
|---|---|---|
| *"not available on the Gemini API but ... available on the Gemini Enterprise Agent Platform"* | Vertex-only, real feature elsewhere | **Keep**, documented as Vertex-only |
| *"Unknown parameter 'x'"* | Absent from the schema entirely | **Remove** |

Kept for parity: `safety_settings`, `Tool::Retrieval`,
`enable_bigquery_tool`. Removed: `response_mime_type` and `cached_content`
(#439). Request `labels` were kept on the same grounds and became accepted
on the Gemini API by 2026-09-24, which is the case for keeping.

**Consequences.** Modeling a field the endpoint rejects is only justified when
the field is real somewhere. `cached_content` shipped as a public builder
method that could only ever produce a 400 — the field was modeled from the
spec, never live-probed, and its test asserted the field *serialized*
correctly, which it did. See D-010.

## D-006 — Model ids live in constants, and only in `src/lib.rs` (2026-08-16)

**Context.** Bumping the model previously meant editing ~600 occurrences of a
string literal. A sweep that size reliably misses a few, and a missed one is
invisible: the test keeps passing against a model nobody meant to still be
using.

**Decision.** `DEFAULT_MODEL` and friends are public constants and the single
source of truth. `tests/model_literals.rs` fails the build on any hardcoded
`"gemini-<digit>"` — or dated agent id such as `"deep-research-preview-04-2026"`
— outside them.

A capability-specific constant is re-pinned *independently* of the default:
it tracks whichever model has the capability, so it goes stale when that model
retires, not when the default moves. `DEFAULT_IMAGE_MODEL` is the one left;
`MINIMAL_THINKING_MODEL` was removed in 0.12.0, when everything text-based moved
to the 3.8 Flash model, which has no `minimal` thinking level.

**Consequences.** In-crate unit tests may use either a constant or the
synthetic `"test-model"`; they exercise serialization round-trips and never
cared which. **This does not extend to non-test code** — a fallback model id
that reaches the wire must be a real one. `AgentBuilder`'s default was once
swept to `"test-model"` on exactly this confusion, which is why the boundary
is stated explicitly rather than left to judgement.

The literal guard cannot protect the constants file itself: its whole job is
to keep ids in that file, so an id that is stale *in* that file is invisible to
it by construction.

*Also stated as a rule in CLAUDE.md (model constants table).*

## D-007 — Breaking changes are preferred over compatibility shims (2026-08-16)

**Context.** Pre-1.0 library tracking a beta API that itself makes breaking
changes.

**Decision.** Break cleanly when it simplifies the API or aligns with
Evergreen principles. Do not add deprecation shims or dual-path
compatibility.

**Consequences.** Consumers pin and read the CHANGELOG. In exchange the
surface stays small and there is no long tail of half-supported spellings.
CHANGELOG entries carry migration notes for anything user-facing.

*Also stated as a rule in CLAUDE.md ("Rules" → "API conventions").*

## D-008 — Tests are organized by feature, not by pattern (2026-08-16)

**Context.** Multi-turn conversation patterns appear across
`multiturn_tests.rs`, `streaming_multiturn_tests.rs`,
`function_calling_tests.rs`, and `interactions_api_tests.rs`. It looks like
duplication.

**Decision.** Tests live with **what they primarily verify**, not with the
mechanics they happen to use. A function-calling test that uses multi-turn is
testing function calling.

**Consequences.** Don't consolidate tests because they share a pattern. Ask
"what is this test primarily verifying?" The payoff is that every test for a
feature is in one place.

*Also stated as a rule in `docs/TESTING.md` ("Live tests" → "Rules").*

## D-009 — Doctests run in CI only; the docs.rs check is stricter than docs.rs (2026-08-16)

**Context.** Doctests add real compile overhead to every local `make test`.
Separately, docs.rs itself only fails on hard errors, not warnings.

**Decision.** `make test` and `make test-all` exclude doctests; CI runs
`cargo test --workspace --doc`, with default features, with all features and
in strict mode. The local docs.rs verification uses
`-D warnings`, deliberately stricter than docs.rs. Not stricter than the CI
gate, though — `rust.yml`'s docs.rs-feature-set step already sets
`RUSTDOCFLAGS: --cfg docsrs -D warnings`, flag for flag, on stable. What the
local run buys is the *toolchain*: docs.rs builds on nightly.
`release.yml`'s validate job does run nightly rustdoc, deliberately without
`-D warnings` — but only once the tag exists, which is the half that
motivates running it by hand first.

**Consequences.** A doctest can break locally without being noticed until CI.
Accepted: CI catches them, and the local loop stays fast. The `-D warnings`
strictness is an early signal, not a prediction of what docs.rs will reject.

*Also stated as a rule in CLAUDE.md ("Commands" and "Release").*

## D-010 — A structural test is not evidence a feature works (2026-08-16)

**Context.** `cached_content` was marked complete in the gap analysis and had
a passing test, `test_with_cached_content_sets_field_and_wire_format`, which
asserted the field serialized to the right wire shape. It did. The API
rejected the request anyway: `400 Unknown parameter 'cached_content'`. The
feature was unusable end to end for its entire shipped life.

**Decision.** A feature is not verified until something exercised it against
the live API. Serialization tests pin the wire *shape*; they say nothing about
acceptance. Where a feature has an observable effect, prefer a behavioral
assertion over a structural one.

**Consequences.** More `#[ignore = "Requires API key"]` integration tests, and
they must fail loudly rather than skip on error — a test that swallows a
request failure and returns early "passes" without reaching the API, which is
the same false confidence one layer down.

Concretely, #434 does this: its video `processing` test asserts a >10x
token-count difference between a clipped and unclipped window rather than
asserting the field serializes, and panics rather than skips when the
request fails.

*See also `docs/TESTING.md` on structural vs semantic assertions.*

## D-011 — Record structural moves (2026-08-16)

**Context.** #265 spent seven months pointing at `genai-client/src/models/shared.rs`,
a path that no longer exists. The crate was restructured with no record, so a
reader could not tell whether the issue was stale or the file was missing.

**Decision.** When directories or modules move, add an entry here saying what
moved and why. Renaming a file is cheap; leaving every issue and comment that
references it silently wrong is not.

**Consequences.** One more step on refactors that relocate code. Skippable for
moves within a file.

## D-012 — `INLINE_VIDEO_MODEL` was a fixture bug, not a model gap (2026-09-24)

**Context.** From 2026-08 the crate shipped `INLINE_VIDEO_MODEL`, documented
as "`DEFAULT_MODEL` rejects inline base64 video with 400 while accepting it by
URI", verified on two model generations. The 2026-09 sweep found the 400 came
from the test fixture: `TINY_MP4_BASE64` was a 0.2-second clip, which yields no
sampled frame at the default ~1 fps. Any clip of 1 second or longer is accepted
inline by 3.6, 3.7 and 3.8 flash; the 0.2s clip is accepted too once
`processing.fps` is raised. The "passes by URI" control used a different, longer
video, so it could not tell the two causes apart.

**Decision.** Removed the constant and replaced the fixture with a 1-second
clip. A capability constant must be backed by a probe that varies only the
capability under test.

**Consequences.** Breaking for anyone who named `INLINE_VIDEO_MODEL`; the
replacement is `DEFAULT_MODEL`. The generic error text (`Request contains an
invalid argument`) is the only symptom of a too-short clip, which is now noted
in `docs/MULTIMODAL.md`.

## D-013 — One module per resource (2026-09-24)

**Context.** Environments were spread over three public modules:
`environment` (the spec), `environments` (the resource) and
`environment_files`. The Files API types lived in `pub(crate) mod http`,
reachable only through piecemeal root re-exports, so `FileUploadResponse`
was `pub` but could not be named.

**Decision.** Moved, per D-011:

| From | To |
|------|----|
| `src/environment.rs` | `src/environments/spec.rs` |
| `src/environments.rs` | `src/environments/mod.rs` |
| `src/environment_files.rs` | `src/environments/files.rs` |
| Files API types in `src/http/files.rs` | `src/files.rs` (public); the HTTP calls stay in `src/http/files.rs` |

The submodules are private; `genai_rs::environments` re-exports all of it.

Each resource's `impl Client` methods moved out of `src/client.rs` into
that resource's module, as `voices` and `credentials` already did;
`client.rs` keeps `Client`, `ClientBuilder` and the interaction methods.
The bare-ID rules are stated once, in each module's `# IDs` section.

**Consequences.** Every root re-export (`genai_rs::X`) is unchanged. The
module paths `genai_rs::environment::*` and `genai_rs::environment_files::*`
are gone; use `genai_rs::environments::*` or the root.

Amended by D-016: a resource module holds its accessor, handle(s) and list
builders. The interaction methods left `client.rs` in D-017.

## D-014 — Split oversized modules; tests in sibling files (2026-09-26)

**Context.** Nine source files had grown past 1,100 lines excluding tests,
with `steps.rs` near 2,900 and `InteractionBuilder` a single 62-method
`impl`. Large files attract unrelated changes and make review diffs hard to
place. The structure audit compared the crate with the codex workspace
(`evansenter/codex`), which targets modules under 500 lines and moves new
code into a new module once a file passes about 800.

**Decision.** Split each along the seams its own section banners already
marked, as pure moves (no logic, signature or public-path change). Per D-011:

| `src/antigravity/mod.rs` | `src/antigravity/`: `error.rs`, `builder.rs`, `agent.rs`, `hook_mapping.rs`, `turn.rs` beside `mod.rs` |
| `src/antigravity/protocol.rs` | `src/antigravity/protocol/`: `mod.rs`, `enums.rs`, `config.rs`, `input.rs`, `output.rs`, `step_update.rs` |
| `src/content.rs`, `src/content_tests.rs` | `src/content/`: `mod.rs`, `serde_impls.rs`, `annotation.rs`, `results.rs`, `video_processing.rs`, `content_tests.rs` |
| `src/response.rs`, `src/response_tests.rs` | `src/response/`: `mod.rs`, `usage.rs`, `views.rs`, `tool_steps.rs`, `step_summary.rs`, `response_tests.rs` |

`genai_rs::antigravity::protocol::enums`); `EnvFilter` directives match by
prefix, so existing filters still select them.

Test names in the split binaries gain their module
(`http_mock_resources`'s `credentials::loud_wire_redacts_credential_secrets`,
the library's `proptest_tests::steps::step_roundtrip`); nextest's
`test(/name/)` filters still match. Counted afterwards, before any
`#[cfg(test)]` module: `src/streaming.rs` 611 lines, the largest

`src/content/content_tests.rs` 1,336, `src/response/response_tests.rs`

names the file, its count and the limit. It measures as this entry does:
an implementation module in `src/` or `genai-rs-macros/src/` by its lines
outside its own `#[cfg(test)]` test modules (`mod tests` or
`mod <name>_tests`), at most 800 (each sits at the end of its file, so
these are the lines before it; one declared earlier would not hide the code
after it); a unit-test file in `src/` (`*_tests.rs`,
`tests.rs`, `proptest_*.rs`) at most 1,500; the shared test modules
`tests/common/` and `tests/live_verbs/` at most 800; and every other file
under `tests/` at most 2,000. "Roughly" is gone: the bar is the number.
Every file was under its bar when the test landed (the largest
implementation module `src/steps/mod.rs` at 774, the largest test file
`tests/antigravity_harness.rs` at 1,808), so it has no allowlist; a file
that must stay over would need an entry there with its reason.

## D-015 — Derive `Serialize`; keep `Deserialize` hand-written (2026-09-26)

**Context.** Evergreen unions such as `Tool`, `Content` and `Annotation` wrote
each variant list three times: the public enum, a private `Known*` shadow that
`Deserialize` parses into, and a manual `serialize_map`. A prototype showed a
full derive can reproduce the `Unknown` fallback (an `untagged` last variant
with `deserialize_with`), and a read-only survey of all 21 hand-written impls
then compared it against current behavior in detail.

**Decision.** Derive `Serialize` wherever the output is byte-identical to the
manual impl, with shared helpers in `src/serde_util.rs`
(`is_none_or_empty`, `serialize_unknown_merged`, `serialize_unknown_data`).
Keep every `Deserialize` hand-written. Deriving it would change behavior in
edge cases:

- an integer `"type"` tag parses as a variant index, so `{"type": 1}` becomes
  a known variant with defaulted fields and loses the rest of its data
  (serde buffers the input for the untagged fallback, and its buffered
  identifier accepts integers);
- duplicate JSON keys fall to `Unknown` instead of last-one-wins;
- the fallback warning can no longer include the parse error, which is how a
  malformed known variant is told apart from a new one.

Converted: `Tool`, `Annotation`, `Content`, `ResponseFormat`,
`TranscriptionMode`, `InteractionInput`, `FunctionResultPayload`,
`RemoteEnvironment`, plus both halves of `ResponseFormatSpec` (an untagged
`List`-then-`Single` derive, equivalent because `ResponseFormat`'s
`Deserialize` never fails). Each was checked against the removed impl by a
temporary 4,096-case property test per variant, and exact-JSON tests now pin
key order, skip rules and `Unknown` merging. `Step`, `StepDelta`,
`ToolChoice`, `VideoProcessing` and the stream types reshape the wire, so they
stay manual.

**Consequences.** One variant list per type is gone and a new field's skip
rule now sits on the field. The derived impls call `serialize_struct` where
the manual ones called `serialize_map`; serde_json output is identical, but a
non-JSON serializer could tell them apart. Field declaration order is now
wire order for these types, so reordering fields is a wire change.

## D-016 — Resource handles (2026-09-26)

**Context.** Each `/v1beta` resource added its methods straight onto `Client`
(`create_webhook`, `list_trigger_executions`,
`upload_to_file_search_store_with_mime`, ...), so one type carried dozens of
`<verb>_<resource>` names. Optional inputs were positional
(`list_agents(None, None, Some(p))`, `update_webhook(id, &u, None)`), and
every list returned one page, leaving each caller to write its own
`next_page_token` loop. The Python SDK groups the same calls per resource
(`client.agents.list(...)`).

**Decision.** Resource methods move to per-resource handles, under these
rules:

1. **Handles.** Each resource has an accessor
   `Client::<resources>(&self) -> <Handle><'_>`. A handle is
   `#[derive(Clone, Copy, Debug)]` and holds only `&'a Client`, so its
   `Debug` is the client's key-redacting one.
2. **Receivers are `self`, never `&self`.** The future of an
   `async fn(&self)` borrows the temporary handle, so storing
   `client.files().get(id)` or writing
   `join_all(ids.map(|id| c.files().get(id)))` fails with E0515 (a
   returned value references a temporary). Taken by value, the handle is
   moved into the future, which then holds only the client borrow.
3. **Required arguments are positional; optional inputs live on a value**
   (`&WebhookUpdate`, `FileUpload`, `PollOptions`, ...). Only lists are
   builders. A single typed trailing `Option<RevocationBehavior>` is the one
   exception, and a `bool` flag becomes its own verb (`force_delete`).
4. **Nested resources** (`environments().files()`,
   `file_search_stores().documents()`) are plain accessors that bind no id:
   the parent id or full name is a method argument, as in Python.
5. **Lists.** `list(..)` returns a `List*<'a>` builder that owns its ids and
   query state. It is configured with `with_*` and ends in `.send()` (one
   page, the existing `*ListResponse`), `.pages()` or `.items()`. The
   streams send nothing until polled, send the page size and filters with
   every page, end after a page whose token is absent or empty, follow an
   empty page that has a token, and stop on the first error without
   retrying. A token already requested (including the starting one) yields
   its page, then `MalformedResponse`, rather than looping forever. An empty
   object is an empty last page. No handle method returns `impl Trait`, so
   the edition-2024 capture rules never come up.
6. **`#[must_use]` goes on the handle and builder types**, each with a
   reason, and on `pages()` / `items()`. Accessors, `list()` and `with_*`
   carry none: a bare `#[must_use]` on a function returning a `#[must_use]`
   type trips `clippy::double_must_use`, which `-D warnings` makes an error.
7. **Streams own a clone of the client.** `pages()` and `items()` return
   `BoxStream<'static, _>`: the builder clones the `Client` (an `Arc`'d
   reqwest client and two strings) and its query state into the stream, so
   a stream can be stored or spawned even when built from a temporary. A
   compile-time assertion keeps `Client: Send + Sync`. The engine is the
   private `src/paging.rs`.

This amends D-013's placement: a resource module holds its accessor,
handle(s), list builders and `impl_list_page!` invocation instead of an
`impl Client` block. `client.interaction()`, `execute` and `execute_stream`
stay on `Client`. The change lands one resource per commit, agents first.

**Consequences.** Breaking for every resource call (D-007); the old-to-new
table is in `docs/RESOURCES.md`. Each resource is one rustdoc page and one
completion list, and lists no longer need hand-written token loops. A
paging stream clones the `Client` once per page request. Adding a list
filter setter, or `IntoFuture` on the builders, is not breaking later.
Streams borrowing the client would avoid those clones, but switching to
owned streams afterwards would change the handle types, so owned streams
were chosen up front.

*Amended 2026-11-07 (#504).* Rules 2 and 6 are checked on every handle,
not only the sampled verbs the compile guard calls: a source scan in
`tests/http_mock_resources/paging.rs` fails on a public handle method that
takes anything but `self` or `mut self`, or returns a value that is
neither `#[must_use]` itself (a `Result`, a handle, a list builder) nor
marked on the method.

## D-019 — A harness version mismatch warns; it does not refuse (2026-11-04)

**Context.** #499 asked for a spawn-time check of the running harness
against `SUPPORTED_HARNESS_VERSION`. The binary has no version flag, but the
wheel's `google_antigravity-<version>.dist-info/METADATA` sits beside it, so
`spawn()` can read it. Warn or error was left open.

**Decision.** `spawn()` logs a `warn!` on a known mismatch, exposes the
version as `AntigravityAgent::harness_version()`, and names a known

fail. The failures a mismatch causes are already loud: an init rejection
with the harness's own reason, or a turn timeout whose diagnosis now names

`tracing` subscriber until something fails, and when it fails the error
says why. Callers who want a hard stop compare `harness_version()` with
`SUPPORTED_HARNESS_VERSION` themselves (`docs/ANTIGRAVITY.md`, "Version
pinning").

## D-022 — Antigravity policies are evaluated client-side; the auto policy runs in the harness (2026-11-05)

**Status: accepted (2026-11-07).** #493 item 6 asked for
harness-side `PolicyConfig` rules; this departs from it and was decided
during the work, not discussed first. The alternative, the Python SDK's
split, is below under Consequences.

**Context.** Since 0.1.23 the Python SDK sends its policies to the harness
as `PolicyConfig` rules: static rules run in the harness's evaluator, and
rules with a `when` condition or an `ask_user` handler come back to the
client as `policyDecisionRequest`s. #493 item 6 asked for the same. Probing
0.1.23 with a scripted model (2026-11-05) showed: the evaluator is itself a
pre-tool hook inside the harness ("denied by pre-tool hook: …"), called
after the client's pre-tool callback, so it sees exactly the calls that
callback sees; it orders rules named tool over wildcard, then deny over ask
over allow; with any rule present it **fails closed** on a call no rule
matches; and the error step a denial becomes carries no tool name.

**Decision.** Keep evaluating policies in this client, in the pre-tool
callback it already answers, with the harness evaluator's precedence and
the Python SDK's features (conditions, ask-user handlers, reasons, names,
server-wide MCP rules). Send only the auto policy to the harness: its
model-judged assessment can run nowhere else, and a call it flags comes
back as a `policyDecisionRequest`, answered by the policy's handler (or
denied).

**Consequences.** Every denial is this client's, so the event stream names
the denied tool and its arguments, and an ask-user handler runs once per
call. Default-open survives without a synthetic catch-all rule. The
precedence change is breaking: two rules of one tier that disagree now
resolve to the safer decision, not the first registered. The cost is the
round trip per tool call that the pre-tool callback already made; static
harness rules would have saved it. Revisit if the harness gains a policy
feature its pre-tool callback cannot express.

The alternative is the Python SDK's: send static rules as `PolicyConfig`
rules for the harness to evaluate, mark rules with a condition or handler
`is_dynamic` so the harness asks about them over `policyDecisionRequest`.
Default-open would then need a catch-all allow rule of the bridge's own,
since the harness fails closed on an unmatched call. It saves the round
trip for static rules, at the cost of the harness's unnamed denials on the
event stream. Neither approach reaches a subagent's own tool calls on
0.1.23: a probe (2026-11-05) sent a harness-side deny rule for
`view_file`, which denied the root agent's call and not the subagent's,
and the pre-tool callback never sees the subagent's calls either.

## D-024 — Continuation without input, the allowlist-disabled form, and `/v1` (2026-11-05)

**Context.** #489 left three API questions open, each awaiting a probe or a
design call. Probed live on 2026-11-05:

- A stored decode continues from `previous_interaction_id` and
  `continuation_token` alone, with no `input`; the crate always sent one.
  Without input and without a token, the API answers a misleading `404
  Model ... not found`.
- `{"allowlist": "disabled"}` is accepted, echoed as `{"allowlist":
  [{"mode": "disabled"}]}`, and blocks egress exactly as `network:
  "disabled"` does (an agent's `curl` gets the egress proxy's 403 under
  both, 200 with no network config). The bindings model it as the
  allowlist's `Disabled` arm.
- `/v1` serves interactions with the `/v1beta` protocol, continuation
  included, plus files and file search stores, and 404s every other
  resource.

**Decision.**

- `InteractionRequest::input` becomes `Option<InteractionInput>`, as the
  bindings have it, rather than staying required with an omit-when-token
  rule hidden in serialization. `InteractionBuilder::continue_decode(&response)`
  builds the input-free continuation from a response, and `build()` keeps
  requiring input outside a continuation, because the API's own error for
  a missing input is misleading.
- `NetworkConfig::AllowlistDisabled` keeps the second disabled form as its
  own variant, so a read round-trips in the bindings' shape, and
  `is_disabled()` answers the question callers ask of either form. Mapping
  it onto `Disabled` would have dropped the `allowlist` key on the way back.
- `ClientBuilder::with_api_version` overrides the version path segment;
  `v1beta` stays the default. No per-resource refusal on a `v1` client: the
  API's 404 is clear, and the set of resources `/v1` serves can grow
  without a crate release.

**Consequences.** A deserialized request without `input` reads as `None`
instead of failing. `TriggerCreateParams` (`CreateTriggerRequest` since
D-028) keeps the old strictness on its own deserialize path: a trigger fires a fresh interaction, never a
continuation, so a missing or misspelled (`inputs`) input in a trigger
config file is still a parse error. Code that matches `NetworkConfig::Disabled` misses the
allowlist form; `is_disabled()` covers both.

## D-026 — `CallableFunction::call` returns a boxed future; `async-trait` is gone (2026-11-06)

**Context.** #490: `CallableFunction` was declared with `#[async_trait]`,
which made `async-trait` part of the public API (a hand-written impl needed
it as a direct dependency) and pulled `syn` 3 into every consumer's build
beside the `syn` 2 everything else uses. Native `async fn` in traits is
stable well within the 1.88 MSRV, but a trait with an `async fn` (or a
return-position `impl Future`) is not dyn-compatible, and the crate holds
tools as `dyn CallableFunction`: `ToolService::tools` returns
`Arc<dyn CallableFunction>`, the `#[tool]` registry holds
`Box<dyn CallableFunction>`, and the auto-function loop and the Antigravity
dispatcher call through those objects, on spawned tasks that need the
future to be `Send`.

**Decision.** `call` returns `FunctionFuture<'a>`, an exported alias for
`Pin<Box<dyn Future<Output = Result<Value, FunctionError>> + Send + 'a>>`:
the type `#[async_trait]` generated, written out. `#[tool]` emits it, so
macro users see no change. No other trait in the crate is async, so
`async-trait` leaves the dependency graph entirely; nothing still uses it.

Rejected: a native `async fn call` plus a second, dyn-compatible trait with
a blanket impl that boxes it. Users would meet two traits, and the `Send`
bound the dispatcher needs cannot be put on a native `async fn` without
return-type notation (unstable), so implementors would have to write
`-> impl Future<Output = ...> + Send` by hand anyway.

**Consequences.** A hand-written impl wraps its body in
`Box::pin(async move { ... })`. One allocation per call, as before.

## D-027 — `GenaiError` variants: one per cause a caller acts on (2026-11-06)

**Context.** #490's audit of `GenaiError`: `Json` had no producer; `Parse`
(an SSE event that does not parse) and `MalformedResponse` (a body that
does not parse) meant the same thing to a caller; `Internal` covered a
file that failed processing, a poll deadline and client-side bugs alike,
told apart only by message; `ClientBuild(String)` dropped the
`reqwest::Error`.

**Decision.**

- `Json` is removed, and `Parse` folds into `MalformedResponse`.
- A poll deadline is `PollTimeout { timeout, message }`, not the existing
  `Timeout(Duration)`. `Timeout` is the request-level timeout and is
  retryable; a poll deadline must not be, because the resource may still
  be processing and re-sending an import makes a second document. The
  message keeps what was awaited, the last state seen and what to do next.
- A resource that reaches a terminal failure (a file, a file search
  document, an import operation's error) is `ProcessingFailed(String)`,
  not retryable: only a new upload recovers.
- `Internal` keeps the client's own failures: a request body that will not
  serialize, and an unexpected failure reading back a document an upload or
  import already made (the message names it).
- `ClientBuild` holds the `reqwest::Error` as its `source()`.
- Amended 2026-11-07 (#504): `Utf8` is removed with its
  `From<Utf8Error>`. Its one producer was the SSE parser, so it was a parse
  failure under another name. Each case goes where its retryability puts
  it: a complete line that is not UTF-8 is `MalformedResponse`, since the
  server sent those bytes and a retry gets them again, and a line the body
  ended inside (a multi-byte character cut in two) is `StreamInterrupted`,
  as any cut-off tail is.

**Consequences.** Code that matched `Internal` and parsed its message for
these cases needs the new arms. `GenaiError` was already
`#[non_exhaustive]`, so the new variants cost wildcard matches nothing.

`CreateEnvironmentRequest`), `VideoProcessingBuilder` was the one builder
whose setters lacked `with_`, and `InteractionResponse`'s collection
accessors returned a `Vec` (fourteen of them) or an `impl Iterator` (six),
with nothing to tell a caller which.

**Decision.** Rename to `FileListResponse`,
`EnvironmentFileListResponse`, `FileSearchDocumentListResponse` and
`CreateTriggerRequest`; the coverage oracle keeps the binding class names
(`legacy.ListFilesResponse`, `triggers.TriggerCreateParams`) it maps them
to. The video-processing setters become `with_start_offset`,
`with_end_offset` and `with_fps`. Collection accessors return a `Vec`: it
is what most of them already returned and what most call sites use
(`.len()`, `.is_empty()`, `.first()`, indexing, a second pass), and the
lists hold a handful of borrowed views of a response already in memory, so
the allocation is noise beside the request that produced it. The `has_*`
checks and the `first_*` helpers walk a private iterator, so they still
allocate nothing.

**Consequences.** A one-time migration for every renamed item; the
CHANGELOG has the table. An accessor added later returns a `Vec` too.

## D-030 — Strict mode is a `--cfg`, not a Cargo feature (2026-11-06)

**Context.** #490: `strict-unknown` was a Cargo feature that turned
Evergreen's lenient reading (D-001) into errors. Cargo features must be
additive, because Cargo unifies them: if any crate in a build enables one,
every crate in that build gets it. A library that turned on
`strict-unknown` for its own tests, or a binary's dev tool that did, made
every other user of genai-rs in the same build fail on the next value the
API added.

**Decision.** Strict mode is `--cfg genai_strict_unknown`, set through
`RUSTFLAGS` (and `RUSTDOCFLAGS` for doctests) or a `.cargo/config.toml`,
which only the person running the build controls, as tokio's
`tokio_unstable` is. `Cargo.toml` declares the cfg under
`unexpected_cfgs`'s `check-cfg`. CI's `Test Suite (strict-unknown)` job
keeps its name (branch protection names it) and runs the suite and the
doctests with the cfg; the Clippy job lints both configurations, and
`make clippy` and `make test-strict` do the same locally, in
`target/strict` so the default build is not evicted.

Rejected: a runtime switch (a global the feature only defaults, or an
environment variable). Deserialization has no context to carry a
per-client setting, so it would be process-global state, still shared by
every crate in the process, and the test suite's 100-odd
`cfg(not(strict))` gates would become runtime skips that pass silently in
the wrong mode.

**Consequences.** `--all-features` no longer covers strict mode, so a
strict build is a separate build. In CI, `RUSTFLAGS` replaces the mold
linker flag the opt-in cargo config sets, so the strict job links with the
default linker.

## D-031 — `with_content()` composes with `with_history()` (2026-11-06)

**Context.** #454: `build()` refused `with_content()` with
`with_history()`. That was a wire fact while content was sent as a bare
content array, since the API's input union has no arm mixing steps and
content. Since #451 content goes out as a single `user_input` step, so the
pair has an obvious meaning, history then this turn, and the error told
callers to build exactly that by hand.

**Decision.** Relax it. Content after history is
`[...history, Step::user_input(content)]`, the arrangement
`with_history()` + `with_text()` already produces for text; `with_text()`
with content is prepended to the content, as it is without history. A live
probe (2026-11-06, `tests/multimodal_tests.rs`'s
`test_image_content_after_history`) sent a text history and then an image
turn: the API accepted it and the model answered from both.

**Consequences.** One input path is no longer unambiguously single-turn;
`docs/BUILDER_API.md`'s composition tree spells the rule out. An empty
content list is now refused in `build()` (#452), since with history it
would otherwise be an empty final turn.

## D-032 — Dated live facts have two homes; everything else states current behavior (2026-11-06)

**Context.** #495: the 2026-11-01 docs audit graded the docs B-, and every
contradiction it found had one cause: a dated live-API fact restated in
several files, with only some copies updated (the 2026-10-01 MCP step shape
in eight places, the `AntigravityConfig` model list in four, the
custom-agent tool subset in four). By the end of #504's WP8 the guides, the
README, the example headers and the rustdoc still restated dozens of them.

**Decision.** A dated live fact is recorded once, in one of two files split
by kind: `docs/ENUM_WIRE_FORMATS.md` for what a value or a shape looks like
on the wire, and `docs/INTERACTIONS_API_GAP.md` for what the API accepts,
rejects and does (its "Live behavior by area" section collects what the
guides rely on). The guides, the README, `CLAUDE.md` and the example headers
state the current behavior without a date and link there. Rustdoc keeps
what a caller needs at the call site, without the date history.

Left where they are: dated comments in tests and fixtures, which are each
test's evidence; `//` comments in `src/` beside the code a dated
observation justifies (why a stream event needs no id, why a key is
scrubbed from the harness's environment), which are that code's evidence in
the same way and change only with it; the reasons in the coverage oracle's
exception lists, which
D-010 asks to be dated; `CHANGELOG.md` and this file, which are history; and
the API revision `2026-05-20`, which is a version name. Antigravity harness
behavior is keyed by the harness version, not a date: the guide and the
rustdoc name the version, and the dated probe record stays in
`docs/ANTIGRAVITY_BRIDGE_DESIGN.md` beside its upgrade table. Where two
recorded facts disagreed, the more recent one won.

**Consequences.** A behavior change is one edit in a home and one in the
sentence that states it, not a search. A guide's reader sees what is true
now, with the evidence one link away.

**Enforcement (amended 2026-11-07, #504's WP21).**
`.github/scripts/check_dated_facts.sh` fails on a date (a day or a month)
in any Markdown file but the two homes above, the harness probe record in
`docs/ANTIGRAVITY_BRIDGE_DESIGN.md`, this file and `CHANGELOG.md`; in a
doc comment of non-test code in `src/` and `genai-rs-macros/src/`,
crate-private items included, since a private item's dated evidence
belongs in a `//` comment; and in any comment in `examples/`, whose bodies
`examples/CLAUDE.md` holds to the header rule. The exceptions above are
read from the tree's structure rather than an allowlist: a file under a
`tests/` directory, a test-only source file (`*_tests.rs`, `proptest_*.rs`,
`src/coverage_oracle/`) or `#[cfg(test)]` item, a `//` comment in `src/`,
a link's target (a home's dated heading), a timestamp in example data, and
the revision `2026-05-20`. It also fails on a code block fenced `ignore`,
in Markdown or in that rustdoc, without an `<!-- ignore: reason -->` line
directly above the fence (CONTRIBUTING.md). `make test-scripts` runs it and
its harness, so the Shell Scripts CI job does too. It cannot tell a dated
fact from any other date in the files it reads, so a date that is not a
fact (a release date in a guide) has to be phrased without one or added to
the script's `NAMES`.

**Amended 2026-11-08 (#504's H6).** A date is no longer only ISO: the
script also reads an unpadded ISO day (`2026-11-5`), a slashed date
(`2026/11/05`, `11/05/2026`), a dotted one (`2026.11.05`, `05.11.2026`),
one dashed with the year last (`11-05-2026`) and one with the month named
(`November 5, 2026`, `Nov 5, 2026`, `5 November 2026`, `November 2026`),
also when hard-wrapped prose breaks it across two lines, since a named
date has spaces to break at. It skips a date followed by a time with
seconds, a timestamp such as an HTTP date in a `Retry-After` example; a
time without seconds is how prose dates an observation, so that date is
read, in every form alike. A date with no year or a two-digit one
(`Nov 5`, `'26`) is not read: matching one would flag ordinary prose. The
reason line on an `ignore` fence is required in every doc comment of
every Rust file, test code and `tests/` included, since those are where a
fence went without one; the date rule still skips them. Three rules keep
every Rust block compiled or explained (D-059): a Rust block nothing
compiles must be `ignore`d with a reason, whether in a Markdown file that
`src/lib.rs`'s `doc_tests` does not include (`CHANGELOG.md` is exempt as
history) or in a doc comment outside the library's non-test code; a fence
tagged `rs` or `Rust`, which rustdoc never compiles, fails anywhere; and a
`text` block may not hold a Rust statement or item header.

## D-033 — The janitor takes a sourceless environment only when it is empty and idle (2026-11-06)

**Context.** The leaked-resource janitor (#492) deletes only resources
that carry a live test's marker, but environments cannot carry one except
in their inline sources: the resource is `id`, `sources`, `network`,
`status`, `file_count`, `size_bytes` and three timestamps, with no name,
label or metadata (google-genai 2.34.0, and a read-only listing of the
shared key on 2026-11-06). The tests' own sourceless environments come
from calls that take no sources: an agent interaction run without an
environment creates one, a fork (`from_environment`) lists none, and so
does a network-only create. The janitor's first cut deleted every
sourceless environment on the key, a person's included.

**Decision.** Narrow the rule to what the data allows: no sources, no
files (`file_count` and `size_bytes` zero or absent), and no activity
within the age floor, an environment's age being the latest of its
create, update and last-access times. Such an environment holds nothing
to lose. A sourceless environment that holds files, a leaked fork for one,
is kept and listed in the run's summary for a person to check. The
workflow header, the script and `docs/TESTING.md` say plainly that opting
in (`JANITOR_DELETE`) deletes every empty, idle, sourceless environment on
the key, whoever made it.

Rejected for now: giving every test's sourceless environment a marker
source (a marked inline environment on each agent interaction, a marker
source on the network-only create) and dropping the sourceless rule. It
changes live tests that would each need a live run to verify, and a fork
lists no sources whatever its parent had, so forks would still need a
rule of their own.

**Consequences.** The rule still matches an empty, idle environment a
person made without sources; whether that is acceptable on the shared key
is the owner's call when setting `JANITOR_DELETE`. On 2026-11-06 the key
held 35 sourceless environments, all empty, 34 of them from July, and a
dry run would have deleted 112 environments (77 holding only fixture
sources, and those 35) and 3 credentials. A leaked fork, which holds its
parent's files, is listed rather than deleted.

## D-034 — Request-side types the API echoes keep an `extra` map too (2026-11-06)

**Context.** D-001 keeps unmodeled fields in a flattened `extra` map, and
`tests/non_exhaustive_responses.rs` checked it for response structs only:
the request-side types listed in its `REQUEST_SIDE` (exempt from
`#[non_exhaustive]` so callers can build them) were skipped silently, and
so was all of `src/antigravity/`. But a stored interaction serves its
request config back (`generation_config`, `safety_settings`,
`webhook_config`), so `SpeechConfig`, `ImageConfig`, `VideoConfig`,
`TranscriptionConfig`, `AllowedTools`, `SafetySetting` and
`WebhookConfig` dropped a field the API adds, under a `GenerationConfig`
that kept its own. Fifteen Antigravity types read from the harness did the
same beside siblings that kept theirs.

**Decision.** Every deserializable struct keeps an `extra` map unless
nothing serves it back, and the guard checks request-side and Antigravity
types too. The exceptions are listed with a reason each: `CRATE_MADE` (the
crate builds them) and `SENT_ONLY` (only sent: the retrieval tool's
configs, which the Gemini API rejects, so no stored interaction holds one;
`FunctionDeclaration`, made into a `Tool::Function` before it is sent;
`WebhookUpdate`; and the harness config, options, question answers and
hook replies). The guard also requires the map to be a flattened map, not
merely a field named `extra`.

**Consequences.** A breaking change for struct literals of the seven
request configs and the Antigravity types (D-007): add
`..Default::default()`. `SafetySetting::new` loses `const`. A caller can
now also send a field of these configs the crate does not model yet, as
`GenerationConfig::extra` allowed.

*Amended 2026-11-07 (#504, WP13).* The request-side unions a stored
interaction serves back keep theirs too: every known variant of `Tool`,
`ResponseFormat` and `TranscriptionMode` has an `extra` map, and
`ToolChoice::AllowedTools` keeps the keys beside `allowed_tools`
(D-037). The guard gained an enum arm: a public enum without
`#[non_exhaustive]`, a deserializable one without an `Unknown` variant, and
a known variant of such a union without an `extra` map each fail it unless
an exemption names them with a reason. A newtype variant always needs one:
its inner type keeps its own fields, but the syntax does not show whether
keys sit beside that value, as they did beside the old
`ToolChoice::AllowedTools(AllowedTools)`. What stays uncovered, each with
its reason in the guard:

- The retrieval tool's configs (`SENT_ONLY` above). The retrieval tool
  itself keeps its `extra`.
- Bare-string forms, which have no fields: `VideoProcessing::Static` and
  `Agentic`, `NetworkConfig::Disabled`, `ToolChoice::Mode` and
  `EnvironmentSpec::Id`. `EnvironmentSpec::Remote` reads the whole object
  into `RemoteEnvironment`, which keeps its `extra`; nothing wraps it.
  `NetworkConfig::AllowlistDisabled`
  is read only when `allowlist` is the object's one key; with another key
  beside it the object is kept whole as `NetworkConfig::Unknown`.
- The untagged unions with no `Unknown` variant, whose arms keep what they
  do not recognize in their own `Unknown` or catch-all: `InteractionInput`,
  `TurnContent`, `ResponseFormatSpec`, `CodeExecutionOutput` and
  `FunctionResultPayload`.
- The known `AutoFunctionStreamChunk` variants: the crate's own
  `{chunk_type, data}` log form, which only the crate writes. The payload
  inside keeps its own `extra`, but no chunk's `extra` (D-054) is
  passed on: `Delta` carries the `StepDelta` alone, and the stream reads
  the other events without yielding them. A key the API adds to an SSE
  event's envelope reaches `execute_stream()`'s `StreamChunk::extra`
  only.
- The Antigravity `InputEvent` arms, `{"<arm>": payload}`: a oneof the
  crate only sends to the harness. A payload struct keeps its own `extra`;
  a bool or string payload has no fields.

*Amended 2026-11-07 (#538).* The known `StreamChunk` variants left the
list above: each keeps the SSE event's keys it does not read in an `extra`
map (D-054), and the guard no longer exempts them.

*Amended 2026-11-09 (I-11).* `AutoFunctionStreamChunk::Delta` left the
list above too: it is `Delta { delta, extra }`, with the `step.delta`
event's `extra` (D-054), and the auto-function stream passes on an event of
a type the crate does not know as `AutoFunctionStreamChunk::Unknown`, where
it dropped it with a warning. The guard's `AUTO_FUNCTION_CHUNK` exemption
is gone. Four chunks keep a row, under two narrower reasons.
`FunctionResults` and `MaxLoopsReached` are made by the loop with no SSE
event behind them (`LOOP_MADE`): its executions, and its verdict once the
rounds run out. `ExecutingFunctions` and `Complete` are its verdict on one
round's `interaction.completed` event (`ROUND_VERDICT`): the interaction
keeps its own `extra`, but the keys beside it in the event are not passed
on, nor are the round's `interaction.created`, `status_update`,
`step.start` and `step.stop` events, which the loop reads without yielding.
Those reach `execute_stream()` only. That line is scope, not principle:
the completed event's map is empty on every event the API sends today, as
`step.delta`'s is, and `Delta` carries its own because I-11 named it.
Carrying the completed event's would make `ExecutingFunctions` and
`Complete(response)`, the pattern every auto-function caller writes for the
stream's last chunk, take an `extra` too: two more breaking changes,
left for the owner to ask for.


## D-035 — A code execution result is a string or content blocks (2026-11-07)

**Context.** google-genai 3.0.0 types `CodeExecutionResultStep.result` as
`Union[List[Content], str]`; the delta's `result` stays a string. The
Gemini API sent the string on every run probed on 2026-11-07, plots and
files included (those arrive in the next `model_output` step). It accepts
the list form back in history, but the model does not see that content.
With `result: String`, a list-form result would have turned the whole step
into `Step::Unknown`.

**Decision.** A new two-arm enum, `CodeExecutionOutput { Text, Contents }`,
for the step's `result`, written back in the form it came in. Not
`FunctionResultPayload`: its `Json` arm and its send-side `From<Value>`
(which wraps arrays) admit shapes this union does not have. Any other shape
fails the field, so the step is kept whole as `Step::Unknown`, as for any
malformed known step. The delta keeps `result: String`; the accumulator
appends a fragment to the string, or, after a list-form `step.start`, to
its trailing text block (a new one when the last block is not text).
`CodeExecutionResultInfo::result` and `successful_code_output()` give the
enum, with `text()` (a `Cow<str>` of the string or the joined text blocks)
and `Display` for the common case.

**Consequences.** Breaking for callers that read `result` as a `&str`
(D-007); the migration is `.text()`, and `println!("{}", r.result)` is
unchanged. A content-block result keeps its images, which a text view
would have dropped.

## D-037 — Known request-side union variants keep `extra`; the unit tools become struct variants (2026-11-07)

**Context.** C1 of the 2026-11-07 grading: `Tool`, `ResponseFormat` and
`TranscriptionMode` read their known variants with derived or field-picking
serde, and `ToolChoice` kept only `allowed_tools`, so a stored
interaction's echoed `tools`, `response_format` and `generation_config`
lost a field the API adds. D-034 had named `Tool` as not covered, and no
guard looked at enums. `Tool::CodeExecution` and `Tool::UrlContext` were
unit variants, with nowhere to keep a field.

**Decision.** Every known variant gets `extra: Map<String, Value>`, read
and written through `src/wire_fields.rs` as `Step`'s is (#491), so an
`extra` entry never shadows a modeled field or `type`. The two unit tools
become `{ extra }` struct variants, built with `Tool::code_execution()` and
`Tool::url_context()`. Rejected: reading a unit tool that carries an extra
key as `Tool::Unknown`, which keeps the data but makes the tool stop
matching `Tool::CodeExecution`. `ToolChoice::AllowedTools(AllowedTools)`
becomes `AllowedTools { allowed_tools, extra }`, as
`NetworkConfig::Allowlist { entries, extra }` is, with
`From<AllowedTools> for ToolChoice`. `TranscriptionMode` gains `smart()`
and `verbatim()`, since a variant literal now needs `extra`. A known variant
with a malformed field is kept whole as `Unknown`; `TranscriptionMode` used
to read its fields leniently instead. Strict mode still does not apply to
these unions (D-001).

**Consequences.** Breaking (D-007) for struct literals of these variants
(add `extra: Default::default()` or use a constructor), for patterns that
list every field (add `..`), for `Tool::CodeExecution` and
`Tool::UrlContext` as values (`Tool::code_execution()`) and patterns
(`{ .. }`), and for `ToolChoice::AllowedTools(x)` (`ToolChoice::from(x)`;
the pattern is `AllowedTools { allowed_tools, .. }`). `ResponseFormat`
grew past clippy's `large_enum_variant` bar inside `ResponseFormatSpec`;
the lint is allowed there, since a request holds one.

## D-038 — The Antigravity enums share `wire_enum!`'s non-string rule but keep their own macro (2026-11-07)

**Context.** C2 of the 2026-11-07 grading: `wire_string_enum!`
(`src/antigravity/protocol/enums.rs`, 17 enums) duplicated `wire_enum!`
and still had the bug `wire_enum!` had fixed: a non-string value read into
`Unknown` was written back as a string, `7` as `"7"`.

**Decision.** Port the fix rather than merge the macros. The rule lives in
two crate-private helpers in `src/wire_enum.rs`, `unknown_type` and
`serialize_wire`, which both macros call, so it cannot drift again: a
non-string value is typed `<non-string: ...>` and written back as its JSON.
The harness enums keep their own macro because they differ on purpose:
strict mode does not apply to the harness protocol, which is internal and
unstable; an unrecognized value is recorded for `drift_report`; and
`as_wire_str` is public, and `all_wire_values` feeds the protocol-drift
guard. Generating them from `wire_enum!` would take three switches on it,
one of them turning strict mode off.

**Consequences.** `unknown_<context>_type()` on a harness enum read from a
non-string value now returns `<non-string: 7>`, not `7`, and
`drift_report` keys it the same way. The enum guard checks both macros'
templates for `#[non_exhaustive]` and an `Unknown` variant.

## D-039 — A chosen Files API upload name stays unmodeled (2026-11-07)

**Context.** google-genai's `files.upload(config={"name": ...})` sends a
chosen `files/<id>` in the upload's start request. Probed live on
2026-11-07: the API accepts it and serves the file under that name, and a
second upload under the same name fails at finalize, after the bytes are
sent, with `409 <id> already exists. (ALREADY_EXISTS)`. So a chosen name
makes an upload idempotent: a retry of one that landed gets the 409
instead of a duplicate file. `UploadFileConfig` is a hand-written class in
`types.py`; D-040 brings it into the bindings snapshot. `FileUpload`, the value `Files::upload` takes, is shared with
`FileSearchStores::upload`, whose documents have no name to choose.

**Decision.** Not modeled for now, and recorded in `docs/RESOURCES.md` and
`docs/INTERACTIONS_API_GAP.md` with the probe's date. Modeling it is an API
shape choice, not a field: a `with_name` on the shared `FileUpload` would
need store uploads to reject it at runtime, so it needs a files-only shape,
either an `impl Into<...>` wrapper like the store's `DocumentUpload` or a
separate verb (which the live-per-handle guard would hold to a live test of
its own). That choice is the owner's; nothing in the crate needs the name
today.

**Consequences.** A caller who wants an idempotent upload has no way to
choose the name; a retry after a lost upload response can leave a duplicate
file, which expires after 48 hours. `legacy.UploadFileConfig` is in the
coverage oracle's `UNMAPPED` list with this reason, so modeling the name
means removing that entry (tracked in #539).

## D-040 — The bindings snapshot carries query parameters, the legacy endpoints and the Api-Revision (2026-11-07)

**Context.** `bindings.json` recorded each `_gaos` endpoint's method and
path only, so a query key the crate misspelled, or one a release added,
was invisible to the sweep and the oracle. The Files, File Search Store,
Document and Operation surface (google-genai's hand-written modules) had
no endpoints in it, and its classes came from a hand-picked
`LEGACY_ROOTS` that left out `Operation`, so a new verb there went
unseen. The `Api-Revision` the crate sends was a hand-kept constant with
two script copies. The published OpenAPI URLs stopped serving around
2026-11-03, and nothing watched them (#511; the URLs' state is recorded
in docs/INTERACTIONS_API_GAP.md, "How to verify API surface").

**Decision.** `dump_bindings_schema.py` records `endpoints` as an object,
each `METHOD /path` with its `query` parameters (the `_gaos/models/`
request class's `QueryParamMetadata` fields, or the `_query` keys the
legacy converters set), and `api_revision` (the bindings'
`*API_REVISION` constant). The legacy modules' endpoints come from the
methods that reach the Gemini Developer API; a full resource name in a
path (`{name}`, `{parent}`) is spelled out from the class's `_list` path
(`fileSearchStores/{}/documents/{}`), and one it cannot place keeps its
name (`{operationName}`), since `{}` would collide. The legacy classes
are the ones those methods' signatures name (return type, `config`,

## D-041 — The next turn halts an abandoned Antigravity turn; dropping it sends nothing (2026-11-07)

**Context.** Dropping a `chat` future or a `send_streaming` stream mid-turn
abandons the turn on this side only. The harness stays inside it, waiting
for a custom tool's result or a hook's verdict that will never come, so the
next `chat` hung until its turn timeout and the one after got the abandoned
turn's reply (G1, #504). Something has to halt the harness's turn before the
next turn sends its input. `Drop` cannot await, so halting when the turn is
dropped means spawning a task to send the halt.

**Decision.** The agent records whether the turn it last drove reached its
end: a `Finished`, a terminal error from the harness (the main trajectory
went idle with an error, or was cancelled, as on a pre-turn denial), or a
turn timeout whose halt-and-drain went quiet. `begin_turn` halts and drains
a turn that did not, before it sends the new input, the way it already
discarded a trigger turn. Any other error (a fatal model error read from a
step, a lost connection, a hook thread that could not start) counts as
unfinished: the harness may still be inside the turn, and a halt sent to an
idle harness does nothing but cost the drain's half-second silence window.
Nothing is sent when the turn is dropped.

**Consequences.** The halt and the next turn's input go out in order from
the same task, so a halt can never arrive after the next input and cancel
the new turn, as one sent from a spawned task could. The cost: until the
next `chat` or `send_streaming`, the harness keeps working on an abandoned
turn (a slow model call, or builtins the turn goes on to run), and the call
after a turn that failed on this side takes half a second longer.
`cancel_handle()` remains the way to stop a turn at once and keep its
partial output. `next_trigger_turn` does not halt an abandoned turn first:
it consumes what is left of it. The scripted cancel tests count halts: a
halt after a turn that ended in any of those three ways fails them.

## D-042 — `spawn()` refuses subagents beside a gate they bypass (2026-11-07)

**Context.** #520. On harness 0.1.23 a subagent's own tool calls reach
neither the pre-tool callback (so neither this client's policies nor the
`on_pre_tool` hook) nor the harness's policy evaluator, and workspace
containment does not confine them (probed 2026-11-05: with deny-all rules,
a denying hook and containment set, a read-only subagent read a file
outside the workspace). `invoke_subagent` also offers the harness's
built-in `research` subagent, so enabling it exposes an ungated agent even
with no subagent added. Until now `spawn()` only warned. The issue listed
three options: refuse at `spawn()` without an explicit opt-in, give
subagents no builtins by default, or report upstream. The owner chose the
first and the third on 2026-11-07.

**Decision.** `spawn()` fails with `AntigravityError::Config` when the
agent offers subagents (`BuiltinTool::InvokeSubagent`, or
`with_define_subagent_tool(true)`) while any gate is set, unless the caller
calls `with_ungated_subagents(true)`. The error names each gate set and the
opt-in. The gates are a pre-tool hook, a client policy that can refuse or
ask (deny, confirm, `ask_user`), the auto policy (the harness-side
`PolicyConfig` this client sends; it runs in the evaluator the probe showed
bypassed, though it was not probed on its own), workspace containment, and
the `run_command` sandbox while `run_command` is enabled (the agent's own;
a subagent's commands are sent with its own capabilities). The setter takes
a `bool` like this builder's other subagent and containment switches
(`with_define_subagent_tool`, `with_workspace_containment`). A report for
upstream is drafted for the owner to file; the scripted test that pins the
bypass, now with the opt-in, fails when a harness release closes the gap.

Three calls made in the work:
- A policy set that only allows (`allow_all()`, `allow(..)`) is not a gate:
  it refuses nothing, so a subagent bypasses nothing. Counting it would make
  the opt-in boilerplate on every subagent agent, since `invoke_subagent`
  is write-capable and the safety gate already demands a policy or hook.
- `define_subagent` counts on its own, though the harness offers it only
  beside `invoke_subagent` (0.1.23, scripted probe), in case a later
  release separates them.
- The sandbox counts only while `run_command` is enabled on the agent: its
  options apply only then (`Capabilities::with_run_command`), so with the
  tool off it confines nothing a subagent could get around.

**Consequences.** Breaking (D-007): an agent with subagents and any gate,
containment by default with a workspace included, no longer starts until it
opts in. The opt-in is a deliberate acknowledgment, not a fix: the
subagent's capabilities remain its only bound. Revisit when the harness
gates subagent calls (the pinned test fails then), at which point the
refusal can go and the setter be removed.

## D-045 — A red push to main escalates under its own issue, and a PR runs Windows (2026-11-07)

**Context.** main's Windows Cross Platform legs failed on eleven pushes in
a row (#518 to #531) on one CRLF-sensitive test, the second such streak
after #486, and nobody noticed: Cross Platform ran only on main pushes,
it is not a required check, and only a scheduled run escalated a failure

from running.

## D-046 — The flakiness report fails on a breached target, and weighs each flake against its own runs (2026-11-07)

**Context.** The Tests/CI bar holds the week's flake rate under 1% (#504),
and the report only printed a line when it was over. A week with no live
test runs read showed a rate of "0.00%". The aggregate, about 0.2%, hid
tests that needed a retry in one run of eight. Failed pull-request runs were
categorized as flakes, so a change under review read as an API outage. The
Windows CRLF break, which failed on every Windows run and nowhere else, was
filed as a "panic". A test that nextest retried to a pass, inside a job that
failed for another reason, was counted as failed. Example smoke runs, which
retry by hand, were not counted at all.

**Decision.** The report exits 3 when the week breaches a target. The
workflow then publishes the report, fails the run, and so escalates like
any red scheduled workflow. The targets:
- the rate is 1% or more;
- no live test runs were read;
- a chronic flake: a test or example that passed only on a retry in more
  than 5% of the runs it ran in, and in at least two of them. The minimum
  of two keeps one unlucky retry of a test that ran a few times, such as
  one added mid-week, from failing the report.

The 1% rate counts live nextest tests only, as before. Examples are counted
and shown with their own share, outside the rate, since an example run is a
whole program and not one test; the chronic rule applies to them as to
tests. A chronic share counts runs that passed on a retry. A run where the
test failed every try is a failure, reported in the failure breakdown.

Only main's failed runs (push, schedule, dispatch on `main`) are
categorized; pull-request and branch runs are counted apart. Their flakes
that passed on a retry still count, since every finished run's retry-job
logs are read. A test is failed when its last try failed. One that failed
every try, only in jobs named for one OS, and in every leg of that OS in
the run (both Cross Platform toolchains), is labelled deterministic on that
OS, per run. A failure on one leg while the other passes is a flake, and so
is one whose legs cannot be listed.

The Code Coverage job writes `cargo llvm-cov report --summary-only` to the
job summary on every run. It uploads to Codecov only when the
`CODECOV_TOKEN` secret is set, and then fails on a failed upload. The owner
added no token.

**Consequences.** The report goes red for as long as a chronic flake
lasts. On its first run that is likely `test_google_search_multi_turn`,
`test_structured_output_with_url_context` and the Antigravity
`cancel_handle` test, from the grading's counts. The escalation issue stays
open, with its streak, until each is fixed. A Windows-only timing flake
that failed on both Windows legs in one run would also be labelled
deterministic; its failure count tells a one-off from a break.

**Amended 2026-11-09 (I-14).** A chronic share now also counts a run in
which the test retried a model-side flake inside itself, which a
`TRANSIENT_RETRIED` marker shows: D-052's amendment of the same date has
the rule and its reasons. The 1% rate is unchanged.

## D-047 — `PollOptions` raises a short interval to 10 ms rather than rejecting zero (2026-11-07)

**Context.** `PollOptions::with_poll_interval(Duration::ZERO)` was taken
as given, so every `wait_until_active` and file search store import wait
sent each status request the moment the last one answered, until the
deadline (120 s by default). On a paused test clock, with reads that answer
at once, such a wait never reached its deadline at all. The fix could
reject zero or raise it to a floor.

**Decision.** Raise any interval under `PollOptions::MIN_POLL_INTERVAL`
(10 ms), zero included, to it, in `poll_interval_or`, where every wait
reads its interval. Rejecting needs an error path that `with_poll_interval`,
a `const fn` returning `Self`, can't carry, so the wait itself would fail.
For an import that is after the import request was sent, and a caller who
retries the call imports a second document. A floor has no failure mode.
10 ms is far below any status request's round trip, so it changes no real
wait, and it is the shortest interval the crate's paused-clock tests use.

**Consequences.** An interval of 1 to 9 ms now polls every 10 ms. The
floor is public, so a caller can read it. It stops a zero interval, not
fast polling in general; an interval just over 10 ms still polls about
once per round trip.

## D-048 — Library code panics only where it says why; tests and examples are exempt per crate (2026-11-07)

**Context.** #504 (C7, C9): nothing stopped a new `unwrap()` or `expect()`
in library code, or an `unsafe` block without a SAFETY comment, and a
poisoned Antigravity stderr-ring mutex panicked every later stderr line and
error message. Two matches on enums the crate defines ended in an
`#[allow(unreachable_patterns)]` wildcard, which hides a variant a change
adds: inside the crate `#[non_exhaustive]` does not apply, so the wildcard
was never needed.

**Decision.**

- `clippy::unwrap_used`, `clippy::expect_used` and
  `clippy::undocumented_unsafe_blocks` are on at warn in
  `[workspace.lints]`, so `make clippy` and CI deny them. A panic that
  cannot happen carries `#[expect(clippy::expect_used, reason = "...")]`
  naming the invariant, on the narrowest item that holds it; `expect` and
  not `allow`, so the attribute fails once the call is gone. Where the
  invariant can be put in the types instead, it is (a `match` on
  `Value::Object` in place of `as_object_mut().expect(..)`).
- A poisoned stderr ring is recovered with `PoisonError::into_inner`: its
  lines stay whole when a panic interrupts a holder.
- Tests are exempt. `clippy.toml`'s `allow-unwrap-in-tests` and
  `allow-expect-in-tests` cover `#[test]` functions and `#[cfg(test)]`
  modules; every integration-test crate root and every example crate root
  also carries `#![allow(clippy::unwrap_used, clippy::expect_used, reason
  = ...)]`, because clippy's test exemption does not reach an integration
  test's helpers (`tests/common/`) or an example's `main`. An example may
  stop on a missing key or a poisoned lock; the library may not. The
  fuzz entry points (`src/fuzzing.rs`) report a failed check by panicking,
  as a test does, and say so at the top of the module.
- `unreachable_patterns` is `forbid`, not left at its default `warn`: a
  wildcard arm after every variant of an in-crate enum is an error, and an
  `#[allow(unreachable_patterns)]` to bring one back fails to compile
  (`E0453`). A wildcard on another crate's `#[non_exhaustive]` enum is
  reachable, so it is unaffected.

Rejected: rewriting the examples' `expect`s into `?`. The one most of them
have reads `GEMINI_API_KEY`, where a panic naming the variable is the
clearest failure an example can give, and the Antigravity examples lock
mutexes inside hook closures that cannot return an error.

**Consequences.** A new test or example crate needs the crate-level allow
if it unwraps outside a `#[test]` function. A new invariant panic in the
library needs its reason written down.

*Amended 2026-11-07 (#504).* The panicking macros follow the same rule:
`clippy::panic`, `clippy::unreachable`, `clippy::todo` and
`clippy::unimplemented` are on at warn. The one library site,
`Client::new`'s documented panic, carries `#[expect(clippy::panic, reason
= "...")]`, and the fuzz entry points' module-level `#![expect]` names
`clippy::panic` beside `clippy::expect_used`. Tests are exempt as before:
`clippy.toml`'s `allow-panic-in-tests`, and all four lints in every
integration-test crate root's allow, for helpers outside a `#[test]`
function. Clippy has no in-tests setting for the other three, so each
crate's `lib.rs` allows them under `#![cfg_attr(test, ...)]`: the
unit-test build compiles `#[cfg(test)]` modules, and the library build,
which `--all-targets` lints as well, still denies them. An example that
uses one adds it to its crate-root allow; none does today.

`clippy::allow_attributes_without_reason` is on as well, in tests too:
every `#[allow]` and `#[expect]` says why in `reason = "..."`, not in a
comment beside it. Where the lint always fires, the attribute is
`#[expect]`, so it fails once nothing needs it (the `unsafe_code` sites, a
test struct whose field is only parsed). A lint that fires in some builds
and not others keeps `#[allow]`: dead code in `tests/common/`, which each
test binary compiles and uses a part of (one allow at its root now, in
place of one per helper), `clone_on_copy` in the `list_builder!` template,
and `ref_option`, a pedantic lint that is off, on the two serde helpers
whose signature serde dictates. Six `#[allow(dead_code)]` on
`#[tool]` functions suppressed nothing, since the registration uses them,
and are gone.

## D-049 — `AntigravityError::WebSocket` keeps its cause as a boxed error (2026-11-07)

**Context.** #504 (C5): `AntigravityError::WebSocket(String)` kept only
the transport error's text, so a caller could not tell a refused
connection from a reset, and an error reporter walking `source()` found
nothing.

**Decision.** `WebSocket { message, source }`, with `source` a
`Box<dyn std::error::Error + Send + Sync>` marked `#[source]`. Every
producer has a cause: a malformed harness URL (`InvalidUri`), the last
failed connect attempt, a failed read or send (`tungstenite::Error`), so
`source` is not an `Option`. The connect loop returns its last attempt's
error directly rather than keeping an `Option` it would have to unwrap.
Boxed rather than `tungstenite::Error`, because the URL case is another
type, and naming `tokio-tungstenite`'s error in the public API would make
its major version part of genai-rs's; a caller who needs it downcasts.
`Display` keeps the cause's text after `message`, as `ClientBuild` and
`StreamInterrupted` do, for callers that print only the top error.

**Consequences.** A pattern on `WebSocket(text)` becomes
`WebSocket { message, source }`. A `tokio-tungstenite` upgrade changes
what a downcast finds, not genai-rs's API.

*Amended 2026-11-09 (I-6).* `Display` no longer carries the cause's
text: an error whose `source()` returns the cause leaves it to the chain,
so a reporter that walks `source()` (anyhow, eyre, a `while let` loop)
prints it once, not twice. A caller that prints only the top error now
sees what was being done, not why; walk the chain for that. The connect
failure `spawn()` reports as `InitFailed` keeps this error as its source
(D-062).

## D-050 — On Windows, discovery tries `localharness.exe` first and keeps the bare name (2026-11-07)

## D-051 — An issue number is a provenance tag or a pointer; only a pointer must name an open issue (2026-11-07)

**Context.** WP15 removed every "See #N" and "Tracked in #N" that sent a
reader to a closed issue for current behavior. Thirty-four `(#491)` tags
in 22 files and seven `(#459)` tags, `src/response/mcp.rs`'s module doc
among them, remained (outside this file and `CHANGELOG.md`), on rules and
code those issues introduced. Both issues are closed, and #504 asked whether such
tags stay.

**Decision.** They stay. A reference is told by what it claims, not by
its form (amended below). A provenance tag names where a rule or a
behavior was decided or found, as a decision number does: `(#N)` beside
it, or "#493 item 3" on what that item added. A closed issue still holds
the discussion behind it, and the rule has not changed because the issue
closed. A pointer claims that the issue holds current status or pending
work ("tracked in #N", "see #N for what is left", "until #N lands", "#N
item M" while that item is still open), so it names an open issue only:
when the issue closes, the outcome is stated in place and the pointer
goes. `CLAUDE.md` states the rule beside D-032's.

Rejected: removing every reference to a closed issue. It would delete the
only link from the `extra` maps to the reasoning behind them, and the
reader of a provenance tag is looking for history, which a closed issue
is. Rejected for now: a check in `check_dated_facts.sh`. Telling an open
issue from a closed one needs the network, which `make test-scripts` does
not use, and a pointer is phrasing, not a pattern the script could find
without guessing.

**Consequences.** A reviewer, not a script, catches a pointer left on a
closed issue. Closing an issue that a pointer names means editing that
sentence in the same change.

**Amended 2026-11-08 (#504's H6).** The decision first told a pointer by
its form, listing "#493 item 7" among the pointers. By that reading the
tags naming #493's items on the code they added (closed #493's provenance)
were pointers to a closed issue, and so were "See #421" in
`api-surface-sweep.yml` and "See #431" in `report_scheduled_failure.sh`,
which name the history behind each. A reference is now told by what it
claims: current status or pending work makes it a pointer, where
something was decided or found makes it a provenance tag, whatever the
wording. A sentence that could be read either way is reworded to say
which it is, as those two now do. Still no check: telling the two apart
means reading what the sentence claims.

**Amended 2026-11-09 (I-19).** A narrow check exists now, one that reads
wording rather than claims. The daily api-surface-sweep runs
`.github/scripts/check_issue_pointers.sh`: it finds the pointer phrasings
above ("tracked in #N", or by, on or at; "see #N for"; "until #N"), on one
line or wrapped across two, in the tracked files outside `CHANGELOG.md`,
`DECISIONS.md`, fixtures and the script harnesses, looks each issue up
with `gh`, and lists every one that names a closed issue, or no issue, on
one rolling `documentation` issue that a clean run closes.
`tests/ci_workflows/sweep.rs` requires the step. It does not judge whether
a listed sentence is a stale pointer or a provenance tag worded like one;
either way the sentence is reworded, as above. It misses a pointer worded
any other way, which a reviewer still catches, and it does not match a
bare "#N item M", the form this decision also gives a provenance tag. It
runs daily, not in `make test-scripts` or on a PR: an issue closed
elsewhere would turn an unrelated PR red.

that no step the report counts runs the helper's offline tests.

## D-053 — `is_retryable` retries 408 and every 5xx but six that name a permanent condition (2026-11-07)

**Context.** `is_retryable()` called every 5xx transient and every 4xx but
429 permanent (#504, Reliability). So a 408, which google-genai retries,
ended a retry loop, and a 501, the API's `UNIMPLEMENTED`, spent its whole
budget on the same answer. google-genai has two lists. Its older client
retries 408, 429, 500, 502, 503 and 504. Its generated Interactions client,
the surface this crate mirrors, retries 408, 409, 429 and every 5xx by
default.

**Decision.** A status is retryable when it is 408, 429, or a 5xx other than
the registered ones whose definition is a condition the same request meets
again: 501 Not Implemented, 505 HTTP Version Not Supported, 506 Variant
Also Negotiates, 508 Loop Detected, 510 Not Extended and 511 Network
Authentication Required. The 5xx default stays retryable, so 507 (temporary
per RFC 4918) and the unregistered codes proxies send (520 to 599) are
retried, as they were. A 408 is safe to re-send even for a create: the
server stopped waiting before the request arrived whole, so it acted on
nothing. 409 stays permanent: Google's `ALREADY_EXISTS` never passes, and
`ABORTED` wants a fresh read rather than the same request. Nothing at 600
or above is a server error. The private `is_retryable_status` in
`src/errors.rs` gives each code's reason.

**Consequences.** The deny-list is the conservative reading: it changes
only the codes whose definition a retry cannot fix and keeps the old answer
for every other 5xx, where google-genai's older allow-list would have stopped
retrying unregistered codes. The cost is that a misbehaving proxy's
permanent unregistered 5xx is retried until the caller's budget runs out,
as before. One 501 can pass: the API also sends it when a remote MCP
server returns an error, which `classify_mcp_create_error` in
`tests/tools_and_config_tests.rs` counts as that server's availability. The
status cannot tell it from a URL that is no MCP server, which fails every
time, and `is_retryable()` does not match message text (the transient 400s
are left out for the same reason), so 501 stays permanent and the docs
tell a caller who wants that one retried to match its message first. The
crate's own waits (`wait_until_active`, an import's wait) poll through
what `is_retryable()` accepts, so they follow this list.

## D-054 — Known `StreamChunk` variants keep the event's unread keys; `Completed` is a struct variant (2026-11-07)

**Context.** #538: a stream's known events kept only their modeled fields,
so a key the API adds beside an event's payload was dropped. The payloads
kept their own `extra` (D-034), but the envelope did not, and the
Evergreen guard exempted all seven known variants for it. The issue named
two shapes: an `extra` map on each known variant, or the raw event JSON,
as `InteractionStreamEvent` keeps for an unknown type.

**Decision.** Each known variant has an `extra` map, read by
`StreamChunk::extra()`, which is what the guard's enum arm checks and how
`Step`, `Tool` and `ToolChoice::AllowedTools` already keep theirs.
`Completed(Box<InteractionResponse>)` becomes
`Completed { interaction, extra }`: a newtype variant has nowhere to put
the map, and the guard needs a named reason for every newtype, which this
one no longer has. A chunk's `extra` holds every key of its event it does
not read:

- a key the crate models on no event type;
- a modeled key on an event type that does not read it (an `index` on a
  `status_update`), as it came: the parser reads only the keys the
  event's type reads, so it neither writes such a key back through the
  crate's type (which would not reproduce it) nor fails the event on a
  value that type could not read;
- what is left of `metadata` beside the `total_usage` a `step.delta` or
  `interaction.completed` reads from it, and of `error` beside its
  `message` and `code`, under that key.

`event_type` is the variant, and `event_id` is on `StreamEvent`, so neither
is in it. A known event is still parsed by value (#498): each key its type
reads is moved out of the object and read, a null modeled key is dropped
as an absent one is, and what is left is the `extra`. The crate's
`{chunk_type, data}` log form writes a non-empty `extra` beside `data` and
reads it back.

Rejected: the raw event JSON on every chunk. It would copy each event
before parsing it, the cost #498 removed from the delta path (a streamed
image delta is the whole base64 image), and would hold every payload
twice. Rejected too: one map on `StreamEvent`. The guard checks the
union's variants, and a chunk is often handled without its event.

**Consequences.** Breaking (D-007): a pattern on `Completed(response)`
becomes `Completed { interaction, .. }`, a pattern listing every field of
a known variant needs `..`, and a struct literal needs `extra`. The
guard's `StreamChunk` exemption and D-034's uncovered bullet are gone. The
auto-function stream passes on no chunk's `extra` (D-034's
`AutoFunctionStreamChunk` bullet), so an envelope key reaches only a
caller of `execute_stream()`.

*Amended 2026-11-09 (I-11).* The auto-function stream passes on a delta's
`extra`: `AutoFunctionStreamChunk::Delta { delta, extra }`, whose
`{chunk_type, data}` form writes and reads it as `StreamChunk`'s does. An
unknown event is passed on as `AutoFunctionStreamChunk::Unknown`, which
writes the `"unknown": true` marker when its type is spelled like a known
`chunk_type`, as `StreamChunk::Unknown` does. The loop's match lists every
`StreamChunk` variant, with no wildcard, so a new one fails to compile
there. The other events' envelope keys still reach only `execute_stream()`
(D-034).

## D-055 — The file watch skips a poll it cannot fully read, and follows a symlinked root (2026-11-07)

**Context.** `triggers::on_file_change` snapshots its tree each poll and
diffs it against the last one. A snapshot whose root could not be read was
already a failed poll (#504, C6), but below the root a directory that
could not be listed, or an entry whose metadata or listing failed, was
left out, so a transiently unreadable directory reported every file in it
deleted, then added back. A watched path that was a symbolic link read as
an empty tree (`symlink_metadata` on the root), where Python's `watchfiles`
follows the root. A zero `poll_interval` walked the tree back to back.

**Decision.** Any I/O or permission error other than not-found, on the
root or below it (metadata, a listing, or an entry the listing yields),
fails the snapshot: the poll is skipped, with a warning when such polls
begin and a debug line for each one after. Not-found means the path went
away, so what was there reads as deleted, as before. A directory in
`IGNORED_DIRS` is never read, so it cannot fail a poll. The root is
followed with `metadata`; entries below it keep `symlink_metadata`, so
links there are still not followed. The interval is raised to
`PollOptions::MIN_POLL_INTERVAL` (10 ms), as D-047 does for status polls.

The alternative for an unreadable directory was to carry the last
snapshot's entries under it forward, treating it as unchanged, which keeps
reporting changes elsewhere while it stays unreadable. Skipping the poll
is the narrower change and cannot invent or hide a change under the
directory; carrying forward can be added if a permanently unreadable
directory in a watched tree turns out to be common.

**Consequences.** A directory that stays unreadable holds back every
change under the watched path until it reads again; the rustdoc and
`docs/ANTIGRAVITY.md` say to keep such directories out of the tree, and
the warning names the entry or directory that failed and its error, so
the user can find it. The baseline taken in `on_file_change` follows the
same rule: when part of the tree cannot be read then, it warns, and the
first snapshot that reads all of it becomes the baseline, so changes made
before that are not reported. A link to a file as the root is that file,
and a dangling root link is an empty tree, like a missing path.

## D-056 — `AntigravityError` names its causes: no `#[from]`, sources on `Protocol` and `Io` (2026-11-07)

**Context.** `AntigravityError` had `Io(#[from] std::io::Error)` and
`Json(#[from] serde_json::Error)`, so any `?` on either became one of
them. An unparsable harness frame came out as `Json`, though `Protocol`'s
doc claimed that case, and `Media::from_file` returned `Io` without the
path it failed to read.

**Decision.** Both `#[from]`s go, and `Json` with them. `Protocol` is
`{ message, source: Option<Box<dyn Error + Send + Sync>> }`: an inbound
parse failure carries the `serde_json` error as its source; a turn that
ended without its final event has none; and an outbound message that would
not encode (none can today) is a `Protocol` error too, since it is the
same contract broken from this side. `Io` is `{ message, source }`, the
shape `WebSocket` has, with the operation and path in `message`: a
`Media::from_file` read, and the one other I/O failure left, harness
discovery cut short by a runtime shutting down. A message the client
sends is serialized in `session.rs` (`send_raw` takes the value), so the
error mapping lives in one place.

**Consequences.** Breaking, with a CHANGELOG migration. `agent.rs`, at 798
of 800 lines, changes on three lines and grows by none: the two
`Protocol(..)` constructions call `AntigravityError::protocol(..)`, and
`initialize` passes the init event to `send_raw`. `Protocol`'s `Display`
carries the parse error's text in `message`, so a printed error still
says what failed.

*Amended 2026-11-09 (I-6).* `Protocol`'s and `Io`'s `Display` no longer
carry the source's text, as D-049's amendment gives for `WebSocket`:
`message` says what was being done, and `source()` says why.

## D-057 — Each harness WebSocket connect attempt times out after 5 s (2026-11-07)

**Context.** `Session::connect` retried up to 5 times with backoff, but an
attempt had no bound: a harness that accepted the TCP connection and
never answered the WebSocket upgrade held `spawn()` forever.

**Decision.** Each attempt (the TCP connect and the upgrade) is bounded by
`CONNECT_ATTEMPT_TIMEOUT`, 5 s, and a timeout counts as a failed attempt,
with an `io::ErrorKind::TimedOut` error as the transport source. The
harness is on localhost and has already written its port, so a healthy
one answers in milliseconds; 5 s is a wide margin for a loaded CI runner
while keeping the worst case, 5 attempts and 1.5 s of backoff, at about
26.5 s, below the 30 s the conversation's initialization then gets. A
bound on the whole connect instead would leave a slow first attempt no
retry.

**Consequences.** A wedged harness fails `spawn()` with `InitFailed` after
about 26.5 s. The paused-clock test checks the attempts, the backoff and
the source.

## D-058 — CI measures what it reports: a coverage floor with the antigravity feature, skip markers across runs, and releases gated on the push run (2026-11-08)

  `tests/ci_workflows/coverage.rs` rejects one under 90%.

## D-059 — Two docs guards, and every Rust block compiled or explained (2026-11-08)

**Context.** #504's final grade put Docs at A-: five contradictions and
five enforcement holes. Two of the contradictions were tables that drift
as files are added (`docs/TESTING.md`'s test kinds called every other
test file live; nine were offline), and nothing required a new guide to
be doctested, nor a Rust block outside the doctested guides to compile;
one sat in a `text` fence.

**Decision.**
- `tests/doc_guards/` checks the test-kind table against the test crates.
  A crate is live when any of its module files has a
  `#[ignore = "Requires API key"]` test, and a guard when its code (not
  its comments or strings) uses the library for nothing but a constant:
  it never names `genai_rs_macros` or `trybuild`, nor `genai_rs` except
  as `genai_rs::SOME_CONSTANT`, which a guard may check the repository
  against. Each crate is in exactly one row, live ones under a kind that
  needs a key, guards in the Guards row. The live row names its files
  instead of saying "the other files", so a new file fails until it is
  placed. A row places a file by naming it as `tests/<name>.rs`, or bare
  in the live row's ``In `tests/`:`` list, outside parentheses; a file
  named inside parentheses is a reference, which only has to exist.
- The same module requires every Markdown file under `docs/`, at any
  depth, and every top-level one with a Rust block (a fence rustdoc
  reads as Rust, or one tagged `rs` or `Rust`), in `src/lib.rs`'s
  `doc_tests`, except `NOT_DOCTESTED`'s four, each with its reason: the
  two maintainer notes, `CHANGELOG.md` and `CLAUDE.md`. An include counts
  where the doctest run compiles it: `src/lib.rs` is parsed with `syn`,
  so a commented-out include is not one, and an include under a `cfg`
  that CI's doctest run (a debug build with every feature on Linux)
  leaves out, such as `cfg(any())`, does not count. An exemption the
  module no longer needs fails too: for a file doctested or gone, or a
  top-level file that holds no Rust any more.
- `check_dated_facts.sh` requires a Rust block that nothing compiles to
  be `ignore`d with a reason, exempting `CHANGELOG.md`'s history. That is

  as the guard does, comments stripped and each `cfg` evaluated), or in a
  doc comment outside the library's non-test code: under `tests/`,
  `examples/` or `fuzz/`, in a test file or `#[cfg(test)]` item, or in a
  module compiled only under such a `cfg`. A block is Rust when its info
  string names `rust`, a rustdoc attribute or an `edition`, and, in a doc
  comment, when it is untagged. A fence tagged `rs` or `Rust` fails
  anywhere: GitHub shows it as Rust, and rustdoc reads it as another
  language and never compiles it. The script rejects Rust in a `text`
  block: a `let` (on one line or several, destructuring, or `let ...
  else`) or `use` statement, a field assignment, a `fn`, `struct`,
  `enum`, `trait` or `impl` header, an `if let`, `while let` or `match`
  header with its body, or a derive, test or tokio attribute. An untagged
  block in a Markdown file that is not doctested counts as text, as
  GitHub renders it.

Rejected: converting `CHANGELOG.md`'s 28 migration blocks to
`rust,ignore` with reasons. They are history, written against the API of
their release, and the reason line would say the same thing 28 times.
Rejected: a looser Rust heuristic for `text` blocks (any `::`, any `;`).
The repository's text blocks hold file trees, wire logs and program

## D-062 — A failed Antigravity turn names its kind, and whether the session survived (2026-11-09)

**Context.** `AntigravityError::Turn(String)` carried every turn
failure, so a caller had to read the message ("model backend error (HTTP
400)") to know whether to respawn, against the guide's "match on
variants, never on message text", and the scripted tests matched on that
text. `spawn()` turned a failed WebSocket connect into `InitFailed` with
the error's text and no `source()`. And `WebSocket`, `Protocol` and `Io`
printed their source's text in `Display` while also returning it from
`source()`, so a chain reporter printed each cause twice (#504's I-6).

**Decision.**
- `Turn { kind: TurnFailure, message }`. `TurnFailure` is
  `#[non_exhaustive]`, `Copy`: `ModelBackend { status }`, `Denied`,
  `Cancelled`, `Trajectory` and `Hook`. The kinds follow what the turn
  loop can tell apart without reading the harness's text:
  - `ModelBackend` for a system error step with an HTTP error status:
    400, 401 and 403 fail the turn at once, as before; any other (a 503
    whose retries ran out) is remembered, and the error that then ends
    the main trajectory is that failure, with its status. The main
    trajectory's first error is remembered too, so it fails the turn
    when it arrives before the terminal update: after a delegation,
    0.1.23 reports a 503 while waiting for subagents and then goes idle
    with no error, and `chat` returned `Ok` with the error in
    `errors()` on a session that was gone. The step's
    `httpCode` holds gRPC codes too (a failed MCP load carries 2), so
    only 400 to 599 count.
  - `Denied` for a turn whose pre-turn hook this client answered with a
    denial, by whichever failing state the trajectory then reaches. The
    hook's verdict is recorded on the turn, rather than the reason
    matched in the harness's message.
  - `Cancelled` for a main trajectory cancelled with no denial;
    `Trajectory` for one that ended with an error otherwise; `Hook`
    for a hook thread that did not start or ended without a result.
- `TurnFailure::ends_session()` is true for `ModelBackend` and
  `Trajectory`. Scripted against harness 0.1.23: 400, 401, 403, a 503
  with no retries, and an MCP server slower than its timeout all end the
  harness's run ("executor run failed") and close the WebSocket; a
  pre-turn denial keeps the session. The tests assert each.
- After a failure whose kind ends the session, the agent fails every
  later call with `ConnectionClosed`, naming that failure, without
  sending. The harness can take one more message before it closes and
  answer it with an empty idle turn, which read as a success on a slow
  CI runner (the design doc's harness record). Rejected: draining before
  the next turn, which cannot tell that empty turn from a real one. The
  refusal is client-side, so a harness that kept its session after these
  failures would not fail the scripted tests: a harness bump re-checks it
  with `LOUD_WIRE=1` on
  `test_scripted_retry_config_decides_whether_a_503_ends_the_turn`. `Cancelled` and
  `Hook` are not taken to end it: no cancellation other than a denial's
  was seen, and a hook failure is this client's, after which the next
  turn halts the harness as for any turn left unfinished.
- `message` is the harness's text (or the hook's reason) alone; the
  error's `Display` names the kind: `agent turn failed (denied by the
  pre-turn hook): <reason>`.
- `InitFailed` has a `source: Option<Box<dyn Error + Send + Sync>>`:
  the `WebSocket` error of a connect that failed, or the error reading
  the harness's initialization reply. `init_failed` and `init_failed_by`
  construct it, so `agent.rs` changes on its constructor lines and grows
  by none.
- No variant's `Display` repeats its source's text (D-049 and D-056,
  amended).

Rejected: a kind for an MCP load failure. The only signal is the
harness's message text, which is what typed kinds exist to stop callers
from parsing; it stays `Trajectory`, whose message names the server.
Rejected: `ends_session()` on `AntigravityError` itself. Whether a
`WebSocket` or `ConnectionClosed` error leaves an agent usable is
already plain (it does not), and the question callers asked was about a
failed turn.

**Consequences.** Breaking, with a CHANGELOG migration: a
`Turn(message)` pattern becomes `Turn { kind, message }`, and
`InitFailed { message, stderr }` gains `source` (match with `..`). A
caller that printed only the top error of a `WebSocket`, `Protocol`,
`Io` or `InitFailed` sees the step that failed, not the cause. The
session-ending claim is the 0.1.23 harness's; a harness bump that keeps
a session after one of these shows up as a failing scripted test.

**Amended 2026-11-10 (PR #548 review, #556).** The backend failure a turn
remembers is the main trajectory's, and only until a later step of that
trajectory follows it. Harness 0.1.23 reports a 503 it is about to retry
with the same system error step as one with no retries left, the retry
following as the next step, so "any other status is remembered" made a
turn that recovered from a retried 503 and then failed on its own (an
unusable model output with no output retries left) a `ModelBackend { status:
503 }`; a subagent's failed call, whose error is not the turn's, did the
same. For the same reason the `AgentEvent::Error` of a 5xx step stays
`Transient`: the step arrives before the harness has retried or given up,
and only its text tells the two apart. Rejected: reading that text
("Encountered retryable error from model provider"). The unit tests feed
each sequence; `test_scripted_a_retried_503_is_a_transient_event_and_not_the_turns_failure`
runs the harness's.

## D-066 — Every message to the harness has a deadline, and a dropped connection reads as closed (2026-11-09)

**Context.** No deadline covered the Antigravity client's WebSocket sends
(#504, I-7). `chat()` and `send_streaming()` sent the message before the
turn deadline started, the halt before a turn went out before the drain
budget started, `Session::close` took the sink's lock outside its bound,
and the send itself had none. A send of 16 MB to a peer that had
completed the upgrade and stopped reading was still blocked after 5 s,
so a wedged harness held a turn with a large prompt (inline media) past
`with_turn_timeout`, against its rustdoc. Separately, a harness that
crashed or was killed ended the connection without a close frame, which
tungstenite reports as an error: the turn failed with a `WebSocket` read
error carrying no stderr, where `ConnectionClosed` says it is for exactly
that case and carries the harness's stderr.

**Decision.**
- A turn's state, and so its deadline, is created before its message is
  sent, and the send is bounded by that deadline alone, however long. A
  send that times out fails the turn with `Timeout` (`agent turn (the
  harness did not take the message)`, the turn timeout) and leaves the
  turn unfinished, so the next turn halts and drains it first (D-041).
- The halt-and-drain budget starts before the halt is sent and bounds the
  send. So do the initialization's budget (`INIT_TIMEOUT`) and the
  session-end budget (`SESSION_END_TIMEOUT`), each 30 s: the wait for the
  answer gets what the send left. An initialization message that fails or
  times out fails `spawn()` with `InitFailed` and the stderr tail, as a
  failed read during initialization already did.
- `close()` takes the sink's lock, sends the close frame and flushes, all
  within its 500 ms.
- Every other send is bounded by `SEND_TIMEOUT`, 30 s, the wait for the
  sink included, and fails with `Timeout` past it: `cancel()`, a
  trigger's delivery, a reply to the harness mid-turn, and the message of
  a turn with no timeout. A harness that reads takes even tens of
  megabytes over loopback in well under a second, so 30 s is never a slow
  harness. A send with a budget of its own goes through
  `Session::send_before`, which has no `SEND_TIMEOUT` inside it, so the
  error names that budget. A mid-turn reply keeps `SEND_TIMEOUT` inside
  the turn deadline: a turn whose timeout is longer fails at 30 s with the
  send's `Timeout` when the harness stops reading mid-turn.
- A read that finds the connection ended without a close frame, or reset
  or aborted by the peer, returns end-of-stream, as a close frame does. A
  turn and `next_trigger_turn` then fail with `ConnectionClosed` and the
  stderr tail, and initialization with `InitFailed`.

Rejected: bounding only the turn's send. It leaves `cancel()`, trigger
delivery and shutdown able to hang on the same harness, and a turn with
no timeout. Rejected: nesting `SEND_TIMEOUT` inside the turn deadline. A
turn under the default 300 s timeout then failed at 30 s, with an
`operation` and `timeout` naming neither the turn nor its budget, against
`with_turn_timeout`'s rustdoc. Rejected: reporting a failed send as `ConnectionClosed`. The
sink handle that cancels and delivers triggers has no harness to read the
stderr from, so sends keep `WebSocket`.

**Consequences.** A send that times out leaves the rest of its frame
queued in the sink, and the next message goes out behind it: if the
harness reads again, it gets the abandoned message, then the next turn's
halt. A paused-clock test drives `chat()` and `send_streaming()` against a
stand-in harness that stops reading, under a 10 s and the default turn
timeout, and another holds the sink across the initialization and the
session-end request (`agent_tests.rs`). `session.rs`'s tests check the
send bound, a send bounded by a later deadline alone, the close bound and
a dropped connection, and the scripted `lifecycle.rs` kills the harness
mid-turn and while `next_trigger_turn` waits.

**Amended 2026-11-10 (J-12, #552).** Two of the bounds above moved to the
turn deadline.
- A reply to the harness mid-turn (a hook's answer, a tool result, a
  question reply, a tool confirmation, a policy decision) goes through
  `send_before` with the turn's deadline, as the turn's own message does,
  and fails with the turn's `Timeout`, naming the reply the harness did
  not take. So a turn whose timeout is longer than 30 s no longer fails at
  30 s when the harness stops reading mid-turn; a turn with no timeout
  keeps `SEND_TIMEOUT`. No reason to keep the 30 s cap inside a longer
  deadline came up: the reply is part of the turn the caller budgeted.
- The turn's state, and so its deadline, is created before `chat()` and
  `send_streaming()` take `turn_sync`, which a trigger's delivery holds
  across its send (up to `SEND_TIMEOUT`). The wait for that lock is
  bounded by the deadline (`agent turn (the harness did not take a
  trigger's message)`), and so is the halt-and-drain of an earlier turn,
  whose five-second budget the deadline cuts short when it comes first;
  a message whose deadline has passed by then is not sent. So `chat()`
  can no longer wait about 35 s before its deadline starts.
  `next_trigger_turn` creates its state, as it documents, at the turn's
  first event, before it takes the lock. A `with_turn_timeout` too large
  to add to the clock (`Duration::MAX`) sets no deadline, as
  `tokio::time::sleep` treats one, where it panicked at the first turn.

Paused-clock tests in `agent_tests.rs` hold a reply's send for 45 s
inside a two-minute turn and past a one-minute one, hold `turn_sync` past
a 10 s turn for `chat()` and `send_streaming()`, hold the halt before a
3 s turn past its deadline, and run a turn with `Duration::MAX`.

## D-067 — `Debug` redacts the secrets `LOUD_WIRE` redacts, outside unmodeled JSON (2026-11-09)

**Context.** The crate's rule is that a type holding a secret prints it
redacted (the `Cargo.toml` lint comment, `CredentialConfig`'s `Debug`,
`docs/LOGGING_STRATEGY.md`), and `Client`, the credential bodies and the
webhook secrets kept it. #504's final grade found six types that derived
`Debug` over one: `ExaAiSearchConfig` and `ParallelAiSearchConfig` printed
their `api_key`, and through `Tool::Retrieval` so did `InteractionBuilder`'s
and `InteractionRequest`'s `Debug`; and the Antigravity endpoints and MCP

decision came with found three more outside Antigravity: `McpServerConfig`

response body whole, a retrieval config's `custom_config` a key nested in

whole in `extra`. So `dbg!(builder)`, `tracing::debug!(?request)` or an
inspector logging `{event:?}` undid the redaction `LOUD_WIRE` applies to
the same fields.

**Decision.** The secrets are the fields `LOUD_WIRE` redacts
(`src/wire/mod.rs`): an `api_key`, a webhook signing secret, credential
material, an environment variable's value, and every value under an MCP
server's `headers` or an allowlist entry's `transform`. Each type that
holds one in a modeled field has a hand-written `Debug` that prints
`[REDACTED]` in the secret's place, `Some("[REDACTED]")` for an optional one that is set, and
keeps the names: the field's, and each header's or variable's, ordered by
name. The impls share `src/redact.rs`, and each destructures its type
without `..`, so a field added later fails to compile until the impl
prints or redacts it. `Tool`'s whole `Debug` is hand-written for
`McpServer`'s headers; its other arms print what the derive did. So the
list is written twice, as the wire's `REDACT_FIELDS` and as these impls: a
name added to one does not reach the other, and the sentinel test is what
holds them together. JSON that carries these secrets by design goes through
the wire's own walk instead (`redact::json`, which redacts and truncates
nothing), so there the one list serves both: a `WireEvent`'s bodies and
payloads (an error body or an SSE frame's `data` is parsed first, and
printed as it is when it holds no secret or is not JSON), and a retrieval
config's `custom_config`. An `env` that `RemoteEnvironment` could not read
prints every string beneath it redacted, since a value cannot be told from
a name there. One unit test, `redact_tests.rs`, formats every type that holds a secret with a
sentinel value, alone and inside the builder, request, response, trigger,
agent and environment that carry it, and fails if the sentinel shows or
the placeholder does not. The types that redacted before are in it, so it
lists the whole set.

Not secrets, and printed as they are: a credential's ID (on an `EnvVar` or
an allowlist entry, which is what the egress proxy looks up), an MCP
server's URL, a decode's `continuation_token`, a webhook's
`truncated_secret` (shown to identify it), and a replicated voice's `key`,
which the API returns in place of an id and a request sends as a voice
name, in the clear on the wire too. Any other free-form JSON prints as it
is, every `extra` map and `Unknown` payload among them: a secret nested
there under a name the wire redacts (an `api_key` in an `extra`) shows in
`Debug` though `LOUD_WIRE` hides it. Redacting it would mean a hand-written
`Debug` on every type with an `extra` map.

Rejected: a newtype for secret strings and header maps. It would change
the type of public fields callers build and match on, for a `Debug` the
impls give without it. Rejected: a derive helper crate (`educe`,
`derivative`) for per-field `Debug` attributes: a dependency for eight
impls. Rejected: leaving `WireEvent`'s `Debug` raw because a custom
inspector receives the bodies raw. It still does, through the fields and
the serialized form; `Debug` is what a log line prints.

**Consequences.** Not breaking: `Debug` output is not a stable format.
The Antigravity types that hold one (`GeminiApiEndpoint`,
`VertexEndpoint`, `McpHttpTransport`, `McpStdioTransport`, `McpServer`,
and the harness options `AgentBuilder`'s `Debug` prints) are the other
half of I-9 in #504. A new type that holds one of these secrets needs its own
`Debug` and a row in the sentinel test; nothing finds it by itself.

**Decision.** A structural move (D-011): `tests/common/source_scan.rs`
holds `rust_files` (every `.rs` file under a root, sorted, failing on a
root that is gone or a directory it cannot read), `parse_file`,
`repo_relative`, `all_items`, `HANDLE_MARKER`, and the discovery:
`structs` (each struct and whether it carries the marker), `handles` and
`public_methods` (each type's public inherent methods in declaration
order). Every walker above and both handle scans use it; what each guard
does with the result, and its floor, stay in the guard (`module_size`'s
more than three files of each kind, `non_exhaustive_responses`'s
non-empty source list and expected test modules, `paging.rs`'s eleven
`HANDLES`, `live_verbs`'s more than fifty live tests). Breaking the shared walker or the handle filter once
failed every one of them.

The file is not declared in `common/mod.rs`, which every integration test
compiles: `module_size.rs` and `non_exhaustive_responses.rs` include it by
`#[path]`, `live_verbs/mod.rs` includes it for `ci_coverage` and
`request_wire_oracle`, and `ci_coverage` reaches it through `live_verbs`,
since a second `mod` of one file in a binary is clippy's `duplicate_mod`.
`paging.rs` includes it for `http_mock_resources`.

**Consequences.** A new guard that walks the source or finds the handles
includes this file rather than writing its own. Two walkers outside the
guards stay: `tests/model_literals.rs` (which also tolerates an unreadable
entry) and `tests/temp_file_tests.rs`'s scan of `examples/` for media
constants.

**Amended 2026-11-09 (I-20).** Four holes in `check_dated_facts.sh`
passed a scratch copy, though no instance was in the tree:
- "A module compiled only under such a `cfg`" held only for a file module
  (`mod x;`): a doc block on an inline item under a `cfg` the doctest run
  leaves out (a `#[cfg(windows)]` fn, an inline `#[cfg(all(test, unix))]`
  mod) passed. The script now evaluates the `cfg` of every inline item, from
  the doc comments and attributes above it to its end, and a file's inner
  `#![cfg]`; an include inside a gated inline module no longer counts.
- It read only `///` and `//!` lines. It now reads every form rustdoc does:
  `/** */` and `/*! */` blocks, and `#[doc = "..."]` and `#![doc = "..."]`
  with their escapes and raw strings. A small lexer finds them, so a string
  literal or a plain comment that looks like one is no longer read as doc
  text either.
- A bare expression in a `text` block passed. A line that ends in `?;` or
  `.await` now reads as Rust; other bare expressions still pass, for the
  reason the looser heuristic was rejected.
- Both `cfg` evaluators, the script's and `tests/doc_guards/`', read a name
  they did not know as false, which `not(..)` turns true, so "counts as
  left out" held only without a `not`. Each now knows what CI's doctest run
  sets (`doctest`, `unix`, `debug_assertions`, every feature,
  `target_os = "linux"`, `target_family = "unix"`) and what it does not
  (`test`, `windows`, `miri`, `fuzzing`, `docsrs`, `genai_strict_unknown`,
  any other `target_os` or `target_family`), and fails on any other name or
  key, such as `target_arch`, naming it. The script evaluates every `cfg` in
  the library's non-test code, so a new one is taught before it lands; not
  one inside an item already left out, such as an inline
  `#[cfg(test)] mod tests`, which the doctest run never compiles.

The known limits are now a bare expression that ends otherwise, and a
cross-reference to another row's file outside parentheses.
